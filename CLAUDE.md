# CLAUDE.md — контекст проекта

Общий контекст для всех сессий Claude Code в этом репозитории и для всей команды.
Если что-то здесь противоречит вашему предположению — прав этот файл, а не предположение.

## Что это

Чат-бот + мини-приложение в MAX для подготовки и согласования документов внутри
компании. Хакатон MAX × Минобрнауки, трек «Эффективный бизнес», команда
**Сибирский Вайб**. Сдача онлайн-этапа — **30.09.2026**, финал — 29.10 в Казани.

**Первоисточник требований — официальный кейс.** Наши внутренние документы ему
подчиняются, а не наоборот.

### Жёсткие гейты: 0 баллов, решение дальше не оценивается

1. Решение не по теме трека.
2. **Бот или мини-апп не запускается, не отвечает или невозможно проверить
   основной сценарий.**
3. Нет презентации.

Отсюда главный принцип: **работающий минимум важнее амбициозного, но хрупкого.**
Любую фичу проверяйте вопросом «повышает ли она риск, что жюри не пройдёт
основной сценарий».

### Ловушки, уже проверенные вручную — не наступайте повторно

- **`spring-ai-bom:1.1.2` в `dependencyManagement` обязателен.** Стартер GigaChat
  объявляет `spring-ai-autoconfigure-*` без версий; без BOM сборка не резолвится.
- **React строго 19.2.8.** В README библиотеки написано «React 18+» — это неверно,
  `peerDependencies` требуют точную 19.2.8.
- **Spring Boot 3.5 в OSS EOL с 30.06.2026.** Выбран сознательно: под срок в две
  недели стабильность экосистемы важнее свежести, а вся команда работает с
  ассистентами, у которых знание Boot 4 / Spring AI 2 заметно слабее. Версии
  запинены, решение объяснено в презентации как осознанное. Миграция на Boot 4.1
  — план после пилота.
- **MAX Bridge не npm-пакет.** Это `window.WebApp`, подключается скриптом в
  `index.html`. Адрес скрипта **не подтверждён** — сверьте с dev.max.ru до сдачи.
- **Образы MinIO живут на quay.io, не на Docker Hub.** `minio/minio` на Docker Hub
  больше не существует, `docker pull` падает с «repository does not exist».
  Правильные координаты — `quay.io/minio/minio` и `quay.io/minio/mc`.
- **Токен бота выдают организаторы** — MAX ограничил создание ботов верифицированными
  юрлицами РФ, физлица зарегистрироваться не могут. Сайт хакатона: «каждой команде
  предоставляется уникальный токен». При этом ограничение №11 кейса говорит
  «учитывайте при создании чат-бота: ник изменить нельзя» — значит, ник, вероятнее
  всего, выбирает команда. Механику уточнить у организаторов. Получение токена —
  **блокирующая зависимость**, а не формальность.
- **Apache POI не используем.** С транзитивными зависимостями ~17 МБ загрузки
  в каждой холодной сборке; с ним сборка ушла за лимит (384 с при 300).
  DOCX читается средствами JDK: это zip-архив с `word/document.xml`.
- **Ссылка на мини-приложение с параметром:** `https://max.ru/<бот>?startapp=<payload>`,
  payload до 512 символов, только `A-Z a-z 0-9 _ -`. Во фронтенде —
  `window.WebApp.initDataUnsafe.start_param`, но доверять можно только значению
  из **проверенной** `initData`. Шаринг ссылок: iOS, Android, веб; десктоп — в разработке.
- **Long polling у MAX Bot API официально не годится для продакшена**, а вместе
  с webhook не работает. Локально — polling, на стенде сдачи — webhook, то есть
  публичный входящий эндпоинт для бота всё-таки нужен.
- **`dependency:resolve`, а не `go-offline`** в Dockerfile бэкенда: замерено на
  этом проекте, 162 с против 238 с при лимите 300 с.
- **Запас по сборке тонкий.** Полная пересборка без кэша: 207 с на каркасе,
  235 с после PDFBox, 384 с с Apache POI (откатили). **Любая новая зависимость
  бэкенда добавляется только вместе с замером** `docker compose build --no-cache`.
  Сеть проверяющего мы не контролируем, запас меньше минуты — это риск гейта.

## Принятые архитектурные решения

### Маршрутизация согласования: шаблон + ограниченные отклонения

Три уровня, в порядке убывания жёсткости:

**1. Шаблон маршрута** — задан для пары «тип документа + организация», владеет им
организация, не автор. Строки `ApprovalRoute` группируются по `stage_order`:

```
stage_order=1, role=ЮРИСТ       ┐ параллельный этап
stage_order=1, role=БУХГАЛТЕР   ┘
stage_order=2, role=ДИРЕКТОР      следующий этап, только после первого
```

Одинаковый `stage_order` = параллельно. Разный = последовательно. Смешанные
маршруты выражаются без единой дополнительной сущности.

**2. Резолюция ролей в людей** — в момент отправки:
- 0 носителей роли → отправка блокируется с внятной ошибкой, не молчаливый слом;
- 1 носитель → подставляется автоматически;
- \>1 носитель → **автор выбирает конкретного человека** из носителей этой роли.

**3. Ограниченные отклонения** — автор может *добавить* дополнительного
согласующего, но **не может удалить обязательных из шаблона**. Маршрут только
растёт. Добавленные помечаются `origin=ADDED_BY_AUTHOR` и видны всем в цепочке.

> **Инвариант: маршрут может быть только расширен относительно шаблона, никогда
> не урезан.** Это и есть баланс между «хаосом» и «излишней жёсткостью».

**Семантика этапа:**
- Этап завершён, когда **все обязательные** участники одобрили (AND).
  Кворум «M из N» — сознательно не в MVP.
- «Вернуть» или «отклонить» — **fail-fast**: висящие шаги этапа получают
  `SKIPPED`, а не удаляются. История остаётся честной.
- Возврат → правка → повторная отправка стартует с первого этапа. Это не
  упрощение, а корректность: документ изменился, прежние одобрения относились
  к другой версии.

**Предпросмотр маршрута** — обязательный экран перед отправкой: автор видит
полностью резолвленную цепочку с именами. Тот же виджет живёт на карточке
документа. Это ответ на «никто не поймёт, где начало и конец цепочки».

### Решения A–E

- **A. Проверка сценария одним человеком.** `DEMO_MODE=true` добавляет на экран
  приветствия кнопку «Открыть демо-компанию» и переключатель «действовать как…»
  между её участниками. Прямая защита от гейта №2. В демо-компании заранее лежит
  заявка на вступление от вымышленного сотрудника — так проверяющий в одиночку
  может пройти и одобрение заявки с назначением ролей. В проде выключен.
  Следствие: у участника **несколько ролей**, не одна.
- **B. Два уровня поддержки документов.** Хранить, версионировать и проводить
  по маршруту можно **любой файл** — это generic-тип, без схемы и без ИИ.
  Поддержанный тип дополнительно получает схему полей, правила, извлечение
  моделью и проверку. Так продукт универсален по рабочему процессу, а объём
  работ по ИИ ограничен двумя-тремя типами.
  Демо: **служебная записка** — глубоко, 8–10 правил; **заявление на отпуск**
  и **заявка на меру поддержки** — по 4–5 правил. Третий тип адресован наружу:
  у него цена ошибки максимальна, а правила имеют источник вида `LEGAL`,
  тогда как у первых двух — `INTERNAL_POLICY`. Это делает различие видов
  правил демонстрируемым, а не теоретическим.
  **Никакой интеграции с ведомствами нет и не имитируется:** после статуса
  «Согласован» автор подаёт документ сам тем каналом, что есть сегодня.
- **C. Собственный API не заявляем.** Наш REST — внутренний для мини-аппа.
  Кейс не даёт за API баллов, но требует `openapi.yaml` + `DATA-API.yaml` и
  включает два дополнительных технических критерия. `springdoc` подключён
  для внутренней работы команды, в сдаче как «собственный API» не фигурирует.
- **D. Spring Boot 3.5.16 + Spring AI 1.1.2.** Обоснование выше.
- **E. Деградация ИИ обязательна.** Недоступность GigaChat не должна ломать
  сценарий — см. README, раздел 12.

### Правки документов

- **Редактора файлов в мини-приложении нет и не будет в MVP.** Править DOCX или PDF
  в браузере на телефоне — это отдельный продукт; встраивание готовых редакторов
  тянет тяжёлые контейнеры и ломает лимит сборки.
- **MUST:** после возврата — загрузка исправленного файла одной кнопкой прямо с экрана
  замечаний, это новая версия. Плюс правка полей и метаданных в форме — та же форма,
  что нужна для ручного ввода при недоступной модели.
- **SHOULD:** служебную записку можно **создать и править прямо в приложении как форму**
  (адресат, от кого, тема, текст). Тогда быстрая правка — это правка формы, а не файла,
  и модель для таких документов вообще не нужна: поля уже структурированы.
  Версия такого документа хранит содержимое в `DocumentVersion.content`, а не файл.
- **Навигация по замечаниям (SHOULD):** у каждого замечания — дословная цитата
  и страница, если формат её даёт. Цитата проверяется на точное вхождение в текст,
  иначе не показывается. У документа-формы нажатие на замечание фокусирует поле.
  Для замечаний «поле отсутствует» места в документе нет по смыслу — а это самый
  частый вид замечаний.
- **Переписывание текста моделью — COULD и только для документов-форм:** модель
  предлагает вариант, автор сравнивает и явно принимает; ничего не применяется
  автоматически. Результат — новая версия, и правила проверяют её заново.
  Набор плейсхолдеров в ответе обязан совпасть с отправленным, иначе предложение
  отбрасывается: модель не должна терять или подменять данные.
- **Переписывание загруженных файлов моделью — WON'T:** нужна генерация файла,
  теряется форматирование, растёт риск выдумки в официальном документе.

### Модель извлекает, код решает

**Языковая модель не решает, нарушено ли требование.** Она делает только одно —
превращает неструктурированный текст в поля. Дальше детерминированный
`RuleEngine` сверяет поля с правилами из базы.

```
файл → извлечение текста → минимизация → маскирование
     → DocumentExtractor (модель)  → поля
     → RuleEngine (обычный код)    → ValidationIssue[]
```

Почему так: результат воспроизводим и тестируется без модели; проверка работает
при недоступной модели по введённым вручную полям; каждое замечание по построению
ссылается на правило, потому что правило его и породило.

### Порты

| Порт | Ответственность |
|---|---|
| `ai/DocumentExtractor` | Текст → поля. Единственное место, где живёт модель |
| `rules/RuleEngine` | Поля + правила → замечания. Обычный код, без модели |
| `storage/FileStorage` | «Положить файл → ключ», «получить по ключу» |
| `security/MaxIdentityVerifier` | Проверка подписи данных запуска мини-приложения |

Провайдер модели выбирается настройкой `app.ai.provider`; смена на YandexGPT,
OpenAI-совместимый эндпоинт или локальную модель не трогает доменный код.
Отдельного слоя `AiProvider` над Spring AI не заводим — Spring AI **и есть**
этот слой, второй был бы обёрткой над обёрткой.

Правило: **никаких классов GigaChat или MinIO за пределами их реализаций.**

### Подключение компании (онбординг) — MUST

Компания подключается сама, без разработчиков. Засеянная база остаётся только
для демо-организации.

```
Первый вход, не состоит в компании
 ├─ «Создать компанию» → название → создатель становится ADMIN
 │     → компании автоматически создаются стандартные роли и маршруты
 │
 ├─ Общее приглашение (код компании) — для рабочего чата
 │     многоразовое, без срока; «Перевыпустить» отзывает старый код
 │     → сотрудник вводит код (или открывает ссылку с кодом) → видит название
 │     → JoinRequest (PENDING) → ADMIN получает уведомление в боте
 │     → ADMIN принимает и на том же экране назначает роли — или отклоняет
 │
 ├─ Личное приглашение — для одного человека                         [SHOULD]
 │     ADMIN заранее выбирает роли (кроме ADMIN) → одноразовая ссылка на 72 часа
 │     → человек открывает → видит компанию и роли → «Вступить»
 │     → вступает сразу, без заявки
 │     → ADMIN получает уведомление «Иванов вступил по вашей ссылке» с кнопкой «Исключить»
 │
 └─ «Открыть демо-компанию» — только при DEMO_MODE=true
```

**Подтверждение зависит от типа приглашения, а не от того, код это или ссылка.**
Код можно переслать в личку, а ссылку — в общий чат. Поэтому правило не «ссылка
без подтверждения, код с подтверждением», а «общее приглашение — с подтверждением,
личное — без». Код компании можно отправить и ссылкой: он всё равно ведёт к заявке.

**Общее приглашение даёт право подать заявку, а не доступ.** Утёкший код не открывает
документы, поэтому он может быть коротким и удобным для ручного ввода.

**Личное приглашение — это предъявительский токен.** Система не знает, кому админ
его отправил: вступит тот, кто откроет первым. Привязать ссылку к получателю нельзя —
идентификатор человека в MAX администратору неизвестен. Поэтому риск утечки
не предотвращается, а ограничивается:
- ссылка одноразовая, живёт 72 часа, неиспользованную можно отозвать;
- роли выбираются при создании ссылки, **роль ADMIN через ссылку не выдаётся никогда**:
  она назначается только явным действием на экране участников;
- при открытии ничего не происходит автоматически — нужна кнопка «Вступить»,
  на экране видны компания и роли, которые человек получит;
- администратор сразу получает уведомление о вступлении и может исключить человека
  одним нажатием.

Отсюда вывод для интерфейса: при создании личной ссылки администратор видит
предупреждение «вступит тот, кто откроет первым — отправляйте только в личные сообщения».

Правила:
- `max_user_id` пользователь не вводит никогда — только из проверенной `initData`.
- Роль себе назначить нельзя. Роли назначает только ADMIN своей организации.
- В маршрутах участвует только **активный** участник с хотя бы одной ролью.
- Отдельной роли OWNER нет: создатель получает ADMIN, а система запрещает
  снять ADMIN с последнего администратора. Этого достаточно против блокировки
  компании, без лишней сущности.
- Новая компания сразу получает стандартные роли (Директор, Руководитель отдела,
  Юрист, Бухгалтер, Кадровик) и стандартные маршруты для поддержанных типов.
  Иначе после создания отправить документ было бы некуда — сценарий бы упирался
  в пустую настройку.
- В MVP пользователь состоит **в одной** компании. Схема допускает несколько,
  интерфейс — нет. Заодно это ограничивает спам созданием компаний.

**Обязательные проверки:**
1. Личность — только из проверенной подписи `initData`, с проверкой давности.
2. Токен личной ссылки — криптографически случайный, не короче 128 бит. Код компании
   для ручного ввода — 8 символов без двусмысленных букв, с ограничением числа
   попыток на пользователя.
2а. Использование личной ссылки **атомарно**: один запрос помечает её использованной
   (`UPDATE ... WHERE used_at IS NULL AND revoked_at IS NULL AND expires_at > now()`).
   Иначе два человека, открывшие ссылку одновременно, вступят оба.
2б. Личная ссылка не может выдать роль ADMIN; набор ролей проверяется при создании
   ссылки, а не при вступлении.
2в. Личная ссылка создаётся только ADMIN; при снятии ADMIN с создателя его
   неиспользованные ссылки остаются действительными, но их видят и могут отозвать
   все администраторы компании.
3. Одобрять заявки и менять роли — только ADMIN **той же** организации. Проверять
   принадлежность заявки или участника к организации администратора, а не только
   сам факт наличия роли ADMIN: иначе администратор одной компании управляет чужой.
4. Заявитель до одобрения не видит ничего, кроме названия компании.
5. Одна активная заявка на пользователя; участник не может подать заявку повторно.
6. Нельзя снять ADMIN с последнего администратора.
7. Нельзя снять роль или отключить участника, у которого есть незавершённые шаги
   согласования: иначе документ зависнет навсегда. Ответ — внятная ошибка.
8. Права читаются из базы на каждом запросе, а не кэшируются в сессии: снятая роль
   действует сразу.
9. Перевыпуск кода компании отзывает старый код. Уже поданные по нему заявки
   остаются на рассмотрении — решение по ним всё равно за администратором.
10. Автор не может согласовывать собственный документ: при разрешении ролей автор
    исключается из кандидатов.
11. Переключатель участника в DEMO_MODE работает только среди пользователей
    демо-организации и никогда не даёт действовать от имени участника реальной компании.

Проверка прав на документы — в сервисе, до любой работы с данными и до модели:
активный участник организации документа, и он либо автор, либо согласующий
на активном этапе, либо документ виден всей организации.

**Идентификатор пользователя берётся только из проверенных данных запуска
и никогда из тела или параметров запроса.** Без этой проверки вся ролевая модель —
декорация.

### Безопасность и работа с ИИ

- Доступ фильтруется по роли и организации **до** модели и **до** интерфейса.
  Не полагаемся на то, что модель «сама не расскажет лишнего».
- **Маскирование именованными плейсхолдерами**, не звёздочками:
  `1234567890 → <INN_1>`, `Иванов И.И. → <PERSON_1>`. Соответствие хранится
  локально и подставляется обратно при показе. Модель видит семантику поля,
  но не значение — при звёздочках она теряет и структуру тоже.
- **Минимизация:** в модель уходит текст, а не файл, и только нужный фрагмент,
  если документ длинный.
- Каждое замечание несёт `rule_id` и источник.
- **Решение по документу модель не принимает никогда.** Только человек.
- **Ноль секретов в репозитории.** Токены — только в `.env` (в `.gitignore`)
  и на служебном первом слайде презентации.
- **Не заявляем соответствие 152-ФЗ.** Обработка у российского поставщика —
  необходимое условие, но не достаточное. В MVP работаем **только на синтетических
  тестовых документах**, и это сказано прямо в README и презентации.

### Статусы документа

`DRAFT → IN_APPROVAL → {СОГЛАСОВАН | REJECTED | RETURNED}`, из `RETURNED`
новая версия возвращает в `IN_APPROVAL`.

Терминальный успех называется **«Согласован»**, а не «Утверждён»: без
квалифицированной подписи «утверждён» вводит в заблуждение и пользователя,
и жюри. Подпись — точка будущей интеграции, а не наш статус.

Отдельного состояния «идёт проверка ИИ» нет намеренно: это операция на секунды,
а как статус документа она создаёт возможность залипнуть в ней навсегда.
Состояние проверки живёт на версии документа, не на документе.

### Версии документа

`Document` хранит метаданные и текущий статус, `DocumentVersion` — файл.
Возврат на доработку создаёт **новую версию**, а не затирает старую.

`ApprovalStep` фиксирует, **какую версию** согласовал человек — иначе история
недостоверна: «Иванов одобрил» без указания версии ничего не значит.

Текущая версия — это поле `current_version_no` (число), а не внешний ключ
на `DocumentVersion`: ключ создал бы круговую ссылку между таблицами.

## Схема БД

Имена сущностей — PascalCase, Spring Data JPA отображает их в snake_case.

| Сущность | Поля |
|---|---|
| `AppUser` | id, **max_user_id (unique)**, full_name, created_at — только личность, без организации и ролей |
| `Organization` | id, name, inn (необязательный, со слов создателя, не проверяется), created_by, created_at, **is_demo** |
| `OrganizationMember` | id, org_id, user_id, **status** (ACTIVE / DISABLED), joined_at; unique(org_id, user_id); в MVP не более одного ACTIVE на пользователя |
| `Role` | id, org_id, code, name, **is_system** — ADMIN системная; остальные создаются компании по умолчанию |
| `MemberRole` | member_id, role_id, **granted_by, granted_at**; PK(member_id, role_id) |
| `Invite` | id, org_id, **kind** (ORG_CODE / PERSONAL_LINK), **code** (8 символов, у ORG_CODE) или **token** (≥128 бит, у PERSONAL_LINK), created_by, created_at, **expires_at** (у личной — +72 ч), **used_at, used_by** (у личной), revoked_at. ORG_CODE — не более одного активного на компанию |
| `InviteRole` | invite_id, role_id — роли, которые получит вступивший по личной ссылке; ADMIN запрещена |
| `JoinRequest` | id, org_id, user_id, invite_id, **status** (PENDING / APPROVED / REJECTED / CANCELLED), created_at, **decided_by, decided_at**; не более одной PENDING на пользователя |
| `DocumentType` | id, name, code, **is_generic** — generic значит хранение и маршрут без схемы и ИИ |
| `DocumentTypeField` | id, document_type_id, field_name, field_type, hint — схема только у поддержанных типов |
| `ApprovalRoute` | id, document_type_id, org_id, **stage_order**, **role_id → Role**, is_mandatory |
| `RequirementRule` | id, document_type_id, field_name, description, **check_type**, expected, **kind**, severity, **source_title, source_url, source_ref, source_checked_at** |
| `Document` | id, document_type_id, author_id, org_id, status, **current_stage**, **current_version_no**, visibility, contains_sensitive, created_at, updated_at |
| `DocumentVersion` | id, document_id, **version_no**, storage_key (null у документа-формы), file_name, mime_type, file_size, **content (jsonb, у документа-формы)**, created_by, created_at, extracted_fields (jsonb), validation_issues (jsonb), check_status |
| `ApprovalStep` | id, document_id, **version_no**, approver_id, **stage_order**, **origin**, decision, comment, created_at, decided_at |

`status`: `DRAFT` / `IN_APPROVAL` / `APPROVED` (Согласован) / `RETURNED` / `REJECTED`.
`decision`: `PENDING` / `APPROVED` / `RETURNED` / `REJECTED` / **`SKIPPED`**.
`origin`: `TEMPLATE` / `ADDED_BY_AUTHOR`. `kind`: `LEGAL` / `INTERNAL_POLICY` / `PRODUCT_RULE`.

Роли — строки в `Role` конкретной организации, а не enum в коде: у разных компаний
разный набор, а универсальность продукта — его суть. В MVP набор создаётся по
умолчанию и через интерфейс не редактируется.

Отдельной таблицы `AuditEvent` в MVP **нет**: история полностью выводится из
`DocumentVersion`, `ApprovalStep`, `JoinRequest` и `MemberRole` — кто, что, когда,
по какой версии и кто кому выдал роль.
Универсальный журнал добавил бы таблицу и запись в каждый путь ради того же самого.

Этап выражен номером `stage_order`, отдельной таблицы этапа нет. Если появится
кворум «M из N» или срок на этап — тогда этап станет своей таблицей, не раньше.

Схемой управляет Liquibase (`db/changelog/`), Hibernate стоит в `ddl-auto: validate`.

## Контракт между Ильёй и Никитой

Чтобы не блокировать друг друга — обмен идёт через порты, не через общий код.
Сигнатуры портов уже в репозитории.

- **Илья:** `FileStorage` (MinIO), `TextExtractor` и `DocumentExtractor` (поля
  из документа), `RuleEngine` (поля + правила → замечания), API документов.
- **Никита:** `MaxIdentityVerifier` и текущий пользователь, подключение компании,
  движок маршрутов и состояния документа, бот. Вызывает порты Ильи, не зная,
  что под ними — GigaChat или MinIO.
- **Фронт ↔ бэк:** `docs/API_CONTRACTS.md` (задача #10). Меняете эндпоинт или DTO —
  обновляете контракт в том же PR.

Задачи, исполнители, сроки и зависимости — в GitHub Issues.

## Экраны

**Подключение компании**
- Приветствие: «Создать компанию» / «Присоединиться» / «Открыть демо-компанию» (только DEMO_MODE).
- Создание компании: название, ИНН необязательно.
- Приглашения (ADMIN): код компании — «Поделиться», «Перевыпустить»; личные ссылки [SHOULD] —
  «Создать» с выбором ролей и предупреждением, список неиспользованных с «Отозвать».
- Присоединение по коду: ввод кода либо автоподстановка из ссылки → название → заявка.
- Вступление по личной ссылке [SHOULD]: компания и роли → «Вступить» → сразу внутри.
  Просроченная, использованная или отозванная ссылка — внятное объяснение и кнопка
  «Присоединиться по коду».
- Ожидание решения, с возможностью отменить заявку.
- Заявки (ADMIN): принять с выбором ролей на том же экране или отклонить.
- Участники (ADMIN): список и изменение ролей.

**Документы**
1. Форма загрузки документа (включая пустое состояние).
2. Результат ИИ-проверки — «есть замечания» и «всё чисто».
3. Предпросмотр маршрута перед отправкой.
4. Экран решения согласующего — документ, данные ИИ, история, кнопки.
5. Список документов — мои / на моём согласовании / общие.
6. Состояния загрузки и ошибки — требование кейса, не опция.

### Что реально есть в `@maxhub/max-ui` 0.5.0

Проверено в установленном пакете:

`Avatar`, `Button`, `CellAction`, `CellHeader`, `CellInput`, `CellList`,
`CellSimple`, `Counter`, `IconButton`, `Input`, `MaxUI`, `Radio`, `Spinner`,
`Switch`, `Textarea`, `ToolButton`, `Typography`.
Хуки: `usePlatform`, `useColorScheme` и другие.

**Чего в библиотеке нет** — придётся делать самим:
layout-примитивов (Grid / Flex / Container / Panel), модальных окон, селектов и
выпадающих списков, вкладок, загрузки файлов, карточек, иконок (их всего 2).

`Dot` **помечен deprecated** — на нём не строить индикаторы статусов.

`Typography` — это составной компонент: `Typography.Title`, `.Text`, `.Body`,
`.Headline`, `.Label`, `.Display`, `.Action`. У `Title` проп `variant`
(`large-strong`, `medium`, …), а **не** `level`.

## Соглашения по коду

**Общее**
- Комментарии и пользовательские тексты — по-русски. Код и имена — латиницей.
  Коммиты: `тип(область): описание по-русски (#задача)` — подробности в CONTRIBUTING.md.
- Не коммитить секреты. Ни временно, ни «потом уберу».
- `package-lock.json` и `pom.xml` коммитятся всегда: кейс требует
  зафиксированный файл зависимостей.
- Код-ревью перед мержем в `main`.

**Backend**
- Слои: `Controller` → `Service` → `Repository`. Сущности JPA наружу не отдаём,
  только DTO.
- Ошибки — через `@RestControllerAdvice`, единый формат ответа. Интерфейс должен
  уметь показать пользователю внятную ошибку: это прямой критерий оценки.
- Никаких обращений к БД из контроллеров.
- Проверка прав — в сервисе, до любой работы с данными.

**Frontend**
- Функциональные компоненты, TypeScript strict.
- Компоненты `@maxhub/max-ui` предпочитать самописным: стиль задаёт библиотека.
- Каждый асинхронный экран обязан иметь три состояния: загрузка, успех, ошибка.
- Запросы — на относительный `/api/...`, nginx проксирует. Абсолютные адреса
  бэкенда в коде не прописывать.

**Git** — полные правила в [CONTRIBUTING.md](CONTRIBUTING.md).
- В `main` напрямую не пушим — только pull request с зелёным CI и одобрением.
- Ветки: `feature/<номер задачи>-<кратко>`, `fix/<номер задачи>-<кратко>`.
- Ревьюеры назначаются по `.github/CODEOWNERS`.
- Репозиторий **один** на всё решение: кейс требует единый commit hash.

## Сдача

Кейс, стр. 9: «Git-репозиторий с commit hash **или** архив с контрольной суммой.
После дедлайна версия не изменяется». Публичность репозитория кейс не требует.

- **Сейчас:** приватный репозиторий на GitHub, доступ только у команды.
- **30.09, после последнего коммита:** тег `submission-online`, репозиторий
  становится публичным, ссылка и commit hash — на первый слайд презентации.
  Дополнительно — архив исходников с SHA-256 как резервный канал.
- **После сдачи и до объявления результатов в `main` не пушим.** Hash и так
  фиксирует версию, но лишние коммиты после дедлайна создают ненужные вопросы.
- Лицензию не добавляем: без неё код по умолчанию защищён, и копировать его
  законно нельзя.
- Приватный репозиторий с доступом «по приглашению» не используем: учётных записей
  проверяющих мы не знаем, а ссылка, отдающая 404, — это «невозможно оценить».
- Точный способ передачи — форма на платформе хакатона; сверить в личном кабинете.

**Работающая версия в MAX** — отдельное требование, стр. 9: «Контейнеризация не
заменяет работающую версию продукта в MAX: чат-бот или мини-приложение должны
оставаться доступны для прохождения основного пользовательского сценария».
Мини-приложение в MAX открывается только по публичному HTTPS — развернуть его
«у себя» проверяющий не может, бот привязан к нашему токену и нашему адресу.
Точной даты окончания кейс не называет; ориентир — период оценки до 14.10.

Docker при этом проверяет **воспроизводимость и код**, а не пользовательский сценарий.
