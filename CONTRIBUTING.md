# Как мы работаем

Короткие правила для всей команды. Архитектура и решения — в [CLAUDE.md](CLAUDE.md),
здесь только процесс: как вести ветки, писать код и сливать изменения.

## Пять правил, которые не нарушаем

1. **В `main` напрямую не пушим.** Только через pull request.
2. **Одна задача — одна ветка — один PR.** Маленький PR проверяется за 10 минут,
   большой — за день или не проверяется вовсе.
3. **Сливаем только с зелёной проверкой CI** и одобрением ревьюера.
4. **Никаких секретов в коде, коммитах, задачах и скриншотах.** Токен бота, ключ
   GigaChat, пароли — только в локальном `.env`. Утёк — сразу пишем Булату.
5. **Новая зависимость — только вместе с замером сборки.** Запас до лимита кейса
   в 300 секунд меньше минуты; одна лишняя библиотека — и мы за гейтом.

## Ветки

```
feature/<номер задачи>-<кратко>    feature/4-initdata-verify
fix/<номер задачи>-<кратко>        fix/12-route-preview-empty
docs/<кратко>                      docs/api-contracts
```

Ветку создаём от свежего `main`:

```bash
git switch main && git pull && git switch -c feature/4-initdata-verify
```

## Коммиты

Формат: `тип(область): что сделано (#задача)`. Тип и область — латиницей,
описание — по-русски.

```
feat(auth): проверка подписи initData (#4)
fix(approval): этап не закрывался при двух одобрениях (#5)
test(rules): проверки REQUIRED и DATE_NOT_FUTURE (#5)
docs(api): контракт списка документов (#10)
build(backend): PDFBox 3.0.8, сборка 235 с (#3)
```

Типы: `feat`, `fix`, `test`, `refactor`, `docs`, `build`, `chore`.
Коммит — одно логическое изменение. «wip», «fix», «правки» — не сообщения.

## Pull request

1. Открывайте PR **черновиком сразу**, как появился первый коммит — так видно,
   кто над чем работает, и конфликты всплывают раньше.
2. Заполните шаблон: какая задача, что сделано, как проверить. В описании
   `Closes #N` — задача закроется сама после слияния.
3. Переведите в Ready for review, когда CI зелёный.
4. Ревьюер назначается автоматически по файлу `.github/CODEOWNERS`.
5. **Ревью — в течение 4 часов в дневное время.** Не успеваете — скажите в чате,
   ревью заберёт другой.
6. Сливает **автор** после одобрения, кнопкой **Squash and merge**, ветку удаляет.
7. Конфликт с `main` — автор подтягивает `main` в свою ветку и решает сам.

### Кто что проверяет

| Что изменилось | Кто одобряет |
|---|---|
| Бэкенд | Второй бэкендер: код Ильи — Никита, код Никиты — Илья |
| Фронтенд | Булат или Никита (Никита — когда затронуты вызовы API) |
| Зависимости, Docker, compose, `.env.example`, CI, CLAUDE.md, документы | Булат |

Так контроль качества есть на каждом PR, а через Булата идёт только то, что
может уронить сборку, сломать запуск у проверяющих или поменять общие решения.

### Что смотрит ревьюер

- Решает ли PR задачу и только её.
- Не противоречит ли CLAUDE.md: статусы, роли, модель не решает, проверка прав
  в сервисе.
- Проверка прав есть **до** работы с данными; идентификатор пользователя — только
  из проверенных данных запуска.
- Нет секретов, нет персональных данных в логах.
- Есть тест на то, что может сломаться: правила, переходы состояний, права.
- Для фронтенда — три состояния экрана: загрузка, данные, ошибка.

## Правила кода

### Общее

- Имена в коде — латиницей, комментарии и тексты для пользователя — по-русски.
- Комментарий объясняет **почему**, а не что: что делает код, видно из кода.
- Форматирование задаёт `.editorconfig` в корне: 4 пробела в Java, 2 в TS, LF.

### Бэкенд

- Пакет по модулю: `ru.sibvibe.approval.<модуль>` — `organization`, `document`,
  `approval`, `rules`, `ai`, `storage`, `bot`, `security`, `config`.
- Слои: `Controller` → `Service` → `Repository`. Контроллер тонкий: принять,
  провалидировать, вызвать сервис, вернуть DTO.
- DTO — `record`. JPA-сущности наружу не отдаём.
- Внедрение зависимостей — только через конструктор (`@RequiredArgsConstructor`).
- Ошибки — исключениями, которые `@RestControllerAdvice` превращает в единый ответ
  `{ "code": "...", "message": "понятный пользователю текст" }`.
  Коды: 400 — неверный ввод, 401 — не подтверждена личность, 403 — нет прав,
  404 — нет такого, 409 — действие невозможно в текущем состоянии.
- Классы GigaChat и MinIO — только внутри их реализаций портов.
- В логи не пишем текст документов, ИНН, СНИЛС, телефоны и initData.
- Миграции Liquibase: **слитый в `main` changeset не редактируем никогда** —
  только новый changeset.

### Фронтенд

- TypeScript strict, функциональные компоненты.
- Структура: `src/api` — запросы, `src/screens` — экраны, `src/components/base` —
  свои базовые компоненты, которых нет в MAX UI.
- Сначала компоненты `@maxhub/max-ui`, своё — только когда нужного нет.
  Реально в библиотеке есть: `Button`, `IconButton`, `ToolButton`, `Input`,
  `Textarea`, `Switch`, `Radio`, `Cell*`, `Avatar`, `Counter`, `Spinner`,
  `Typography`. **Нет:** карточки, бейджа, модального окна, списка, выпадающего
  списка, вкладок, загрузки файла — это пишем сами.
- Отдельного npm-пакета SDK MAX нет: мост — это `window.WebApp` из скрипта в `index.html`.
- Запросы — только на относительный `/api/...`.
- **В переменные `VITE_*` ничего секретного**: они вшиваются в бандл при сборке
  и видны любому. По той же причине от них не зависит поведение, которое должно
  меняться без пересборки — например, показ демо-режима: его сообщает бэкенд.
- Бизнес-правила не дублируем на фронте: что разрешено — решает бэкенд, фронт
  показывает его ответ.

## Контракт между фронтом и бэком

Лежит в `docs/API_CONTRACTS.md`. Меняете эндпоинт или DTO — обновляете контракт
**в том же PR** и пишете в чат, если изменение ломающее.

## Работа с ИИ-ассистентами

- Перед задачей попросите ассистента прочитать `CLAUDE.md` и текст задачи.
  Номер задачи в первом сообщении экономит лимиты: не придётся пересказывать контекст.
- **Код, сгенерированный ассистентом, — ваш код.** Вы его читаете, понимаете
  и отвечаете за него на ревью и на защите.
- Ассистент предлагает новую зависимость — сначала замер сборки, потом решение.
- Токены и ключи в промпты не вставляем.

## Токен бота

Придёт на почту Булату. Передаётся **только в личном сообщении**, не в общем чате
и не в задачах. Хранится только в локальном `.env`. Если токен где-то засветился —
сразу сообщаем Булату, он просит организаторов о перевыпуске.
