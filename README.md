# Согласование документов в MAX

> **Статус: каркас.** Бизнес-логика ещё не реализована. Разделы с пометкой
> `[ЗАПОЛНИТЬ]` дописываются по мере готовности функциональности.
> Структура README соответствует требованиям раздела «Формат сдачи» кейса.

Хакатон MAX × Минобрнауки России · трек «Эффективный бизнес» · команда **Сибирский Вайб**

## 1. Назначение решения

Чат-бот с подключённым мини-приложением в MAX для подготовки и согласования
документов внутри компании.

Автор загружает документ, ИИ извлекает из него поля и сверяет их с чек-листом
требований, показывая замечания со ссылкой на конкретное правило. Документ идёт
по маршруту согласующих с уведомлениями в боте. Решение «одобрить / вернуть /
отклонить» всегда принимает человек — модель не решает ничего.

## 2. Основной пользовательский сценарий

`[ЗАПОЛНИТЬ — пошагово, от подключения компании до статуса «Согласован»]`

Кратко:

0. Подключение компании: администратор создаёт компанию и делится приглашением,
   сотрудник подаёт заявку, администратор принимает её и назначает роли.
1. Вход в мини-приложение из бота. Личность — из подписанных данных MAX,
   роли — назначенные администратором; сам пользователь ничего не выбирает.
2. Мини-апп → форма загрузки документа.
3. ИИ-проверка → замечания со ссылкой на правило, либо «всё чисто».
4. Предпросмотр маршрута → отправка на согласование.
5. Согласующие получают уведомления в боте и принимают решения в мини-аппе; если решение
   затягивается дольше двух суток, бот присылает напоминание (настройка `REMINDERS_*`).
6. После последнего одобрения — статус «Согласован» и уведомление автору.

## 3. Состав и архитектура решения

| Компонент | Технология | Назначение |
|---|---|---|
| `backend` | Java 21, Spring Boot 3.5.16 | REST для мини-аппа, стейт-машина согласования, интеграция с Bot API, ИИ-пайплайн |
| `frontend` | React 19, Vite, `@maxhub/max-ui` | Мини-приложение MAX |
| `postgres` | PostgreSQL 16 | Метаданные: пользователи, документы, маршруты, этапы |
| `minio` | MinIO (S3-совместимое) | Файлы документов. В БД только `storage_key` |
| GigaChat | внешний HTTPS-сервис | Извлечение полей и краткой сводки из текста. Нарушено ли правило, решает код |

Схема БД и границы модулей — в [CLAUDE.md](CLAUDE.md).

## 4. Запуск: одна команда

```bash
cp .env.example .env && docker compose up --build
```

Перед запуском заполните `.env` (см. раздел 6). После старта:

- Мини-приложение — http://localhost:8081
- API бэкенда — http://localhost:8080
- Консоль MinIO — http://localhost:9001

Проверено: полная пересборка без кэша — **235 с** при лимите кейса 300 с
(без учёта первоначальной загрузки базовых образов). Все сервисы поднимаются
в состояние `healthy`, бакет MinIO создаётся автоматически.

> Контейнеры — для воспроизводимой проверки. Рабочая версия продукта живёт
> в MAX: ссылка на бота и мини-приложение — на первом слайде презентации.

## 5. Необходимые параметры окружения

| Параметр | Обязателен | Назначение |
|---|---|---|
| `DB_PASSWORD` | да | Пароль Postgres. Без него compose не стартует |
| `MINIO_ACCESS_KEY` | да | Ключ доступа MinIO (≥ 3 символов) |
| `MINIO_SECRET_KEY` | да | Секрет MinIO (≥ 8 символов) |
| `MAX_BOT_TOKEN` | да | Токен чат-бота, выдаётся организаторами |
| `MAX_MINI_APP_URL` | да | Публичный HTTPS-адрес мини-аппа |
| `GIGACHAT_CREDENTIALS` | нет | Authorization key GigaChat. Без него ИИ-сверка деградирует (раздел 12) |
| `GIGACHAT_CLIENT_ID` | нет | Идентификатор проекта GigaChat; секрет уже входит в Authorization key |
| `GIGACHAT_MODEL` | нет | Модель извлечения полей; по умолчанию `GigaChat-2-Max` |

## 10. Порядок работы с тестовыми данными

`[ЗАПОЛНИТЬ — состав сид-данных: организация, пользователи, роли, тип документа,
маршрут, набор правил]`

**Переключатель участника (`DEMO_MODE=true`).** Основной сценарий требует
нескольких людей с разными ролями: автор, затем согласующие. Чтобы один
проверяющий мог пройти цепочку целиком, в мини-аппе предусмотрен явный
переключатель «действовать как…» между предзаготовленными демо-участниками.

Это **механизм проверки, а не часть продукта**: он включается переменной
окружения и в рабочем режиме выключен. Реальный путь — идентификация
пользователя средствами MAX.

## 11. Описание работы с данными

- **Файлы документов** — в MinIO. В Postgres хранится только `storage_key`,
  бинарники в БД не попадают.
- **Метаданные и результаты ИИ** — в Postgres.
- **Доступ** фильтруется по роли и организации **до** обращения к LLM и **до**
  отдачи данных в интерфейс.
- **Маскирование ПДн.** Структурные идентификаторы (ИНН, СНИЛС, паспорт,
  телефон) заменяются плейсхолдерами регулярными выражениями **перед**
  отправкой в облачную модель. Реальные значения подставляются обратно
  локально при показе пользователю.
- **Флаг «содержит чувствительные данные».** Если автор его выставил, сырой
  файл не уходит в модель вообще: автор заполняет поля формой вручную, и
  проверка идёт по введённым значениям.
- **Привязка к источнику.** Каждое замечание ИИ ссылается на конкретное
  правило (`rule_id`), а не является свободным текстом модели.

**Правила проверки: шаблон и настройки компании.** Справочник правил (`requirement_rule`) — шаблон сервиса,
одинаковый для всех компаний; полный список с источниками — [docs/RULES.md](docs/RULES.md). Компания хранит только
отличия от шаблона (`organization_rule_setting`, по одной строке на изменённое правило), правила не копируются:
- администратор в «Компания» → «Правила проверки» выключает правило, меняет важность, текст замечания и
  документ-основание с пунктом, а у проверок «Не короче» и «Одно из значений» — ожидаемое значение;
- правила вида «Закон» не выключаются и не меняются: закон одинаков для всех. Шаблоны формата и формат даты
  не открываются — ошибка в них молча ломала бы проверку;
- рекомендация сервиса, которой компания указала свой документ, становится правилом компании;
- замечания — снимок на момент проверки. Изменённые правила действуют на новые проверки; черновик или
  возвращённый документ автор перепроверяет кнопкой «Проверить заново» — по сохранённым полям, без модели;
  документы на согласовании не пересчитываются.

**Модельные данные.** Чек-лист требований — это заранее подготовленный набор
правил в базе, а не живой запрос в государственную информационную систему.
Интеграция с ГИС в решении **не имитируется**: её нет, и это зафиксировано
здесь и в презентации.

## 12. Поведение без GigaChat

Недоступность внешней модели не ломает сценарий:

1. **Ключ есть, сервис отвечает** — полный разбор документа моделью: поля и краткая сводка «Кратко от ИИ»
   (#92) получаются **раздельными** запросами — общий промпт на оба сразу когда-то сдвигал модель к
   домысливанию дат в самих полях. Сводка показывается только после проверки, что каждое число и дата
   дословно присутствуют в тексте документа. Модель не оценивает документ, не рекомендует
   решение и не влияет на результат детерминированных правил.
2. **Ключа нет, таймаут или ошибка** — документ всё равно принимается и уходит
   по маршруту. Детерминированные проверки (наличие обязательных полей, формат
   значений) выполняются локально и продолжают давать замечания. Интерфейс
   честно сообщает, что разбор моделью недоступен, и не выдаёт отсутствие
   замечаний за успешную проверку. Блок «Кратко от ИИ» в этом режиме отсутствует.
   У версии с флагом чувствительных данных текста и сводки в модели также нет.
3. **`AI_ENABLED=false`** — обращения к LLM отключены полностью.

## 13. Пошаговый сценарий проверки

Один проверяющий проходит весь путь документа сам: в демонстрации он по очереди действует от имени
автора и каждого согласующего. Нужен только MAX — на телефоне или в веб-версии https://web.max.ru.

**Демонстрация** на стенде включена. При своём запуске (`docker compose up`) её включает `DEMO_MODE=true`
в `.env`, иначе кнопки «Посмотреть демонстрацию» на шаге 2 не будет.

**Тестовые файлы** — в [`testdata/documents`](testdata/documents): `02_memo_errors.docx` (служебная записка
с ошибками), `01_memo_ok.docx` (та же без ошибок), `12_act_errors.pdf` (любой другой документ). Откройте файл
и нажмите «Download raw file». Чтобы загрузить его с телефона, отправьте файл себе в MAX в «Избранное» и
сохраните в «Файлы» телефона. Подойдёт и свой DOCX или PDF с текстом — только без настоящих персональных данных.

1. **Бот.** В MAX найдите `t354_hakaton_max_bot`, откройте «Хакатон МАХ 354», нажмите «Начать».
   → Приветствие и кнопка «Открыть мини-приложение».
2. **Мини-приложение.** «Открыть мини-приложение».
   → Экран «Согласование документов»: три пункта о сервисе и кнопки «Создать компанию»,
   «Посмотреть демонстрацию», «Присоединиться по коду».
3. **Демонстрация.** «Посмотреть демонстрацию».
   → Главная демо-компании: четыре плитки — «На моём согласовании», «Мои документы», «Общие документы»,
   «Компания» — и внизу «Новый документ». Вверху плашка «Демо · вы действуете как Демо Автор…» — нажав на неё,
   вы выбираете, от имени какого сотрудника работаете.
4. **Документ с ошибками.** «Новый документ» → зона «Выберите файл документа» → `02_memo_errors.docx` →
   «Далее: проверить документ».
   → До минуты. Шаг 2 из 3 «Проверка». Вид «Служебная записка» определён автоматически (✦ — значение от ИИ).
   Критичные замечания: нет адресата и дата в будущем; предупреждения: заголовок не с «О» и в подписи полное имя.
   У каждого — основание (ГОСТ Р 7.0.97-2016 и т. п.). Ниже — «Данные документа»: что распознано и из какого места
   текста. Отправить пока нельзя.
5. **Исправление.** «Изменить» у «Данных документа» → Адресат `Генеральному директору Орлову В.П.`,
   Дата `15.09.2026`, Заголовок `О закупке ноутбуков для отдела продаж`, Расшифровка подписи `А.С. Петрова`
   → «Исправить и проверить».
   → Значения вписаны прямо в файл Word — версия 2, проверена заново, замечаний нет. Адресата в файле не было,
   поэтому он сохранён в данных документа с пометкой «в файле этого нет» — согласующие это увидят.
6. **Маршрут.** «Далее: выбрать согласующих».
   → Шаг 3 «Маршрут»: этап 1 — Демо Юрист и Демо Бухгалтер одновременно, внизу блок «Утверждение» —
   Демо Директор (у обязательного — замок). Людей можно перетащить за ⋮⋮ или перенести через меню.
   «Отправить на согласование».
   → Карточка: «На согласовании», на таймлайне «Сейчас здесь» — у этапа 1.
7. **Согласующие.** Плашка вверху → «Демо Юрист» → «На моём согласовании» → документ → «Согласовать».
   Затем так же «Демо Бухгалтер», потом «Демо Директор» → «Утвердить».
   → Статус **«Утверждён»**, на таймлайне все этапы пройдены, у каждого — решение и время.
8. **Возврат.** Плашка → «Демо Автор» → «Новый документ» → `01_memo_ok.docx` → «Далее: проверить документ» →
   «Далее: выбрать согласующих» → «Отправить на согласование». Плашка → «Демо Юрист» → этот документ →
   «Вернуть на доработку» → комментарий `Уточните заголовок` → «Вернуть».
   → «Возвращён». Плашка → «Демо Автор» → документ: видна причина возврата. «Исправить документ» → «Изменить» →
   Заголовок `О закупке ноутбуков для отдела продаж в октябре` → «Исправить и проверить» →
   «Далее: выбрать согласующих» — маршрут прошлой версии подставлен сам → «Отправить на согласование»: документ
   изменился, поэтому согласование снова с первого этапа. Плашка → «Демо Бухгалтер» → этот документ: «Изменения
   с версии 1» — было и стало.
9. **Отклонение.** Тот же документ, как «Демо Бухгалтер»: «Отклонить» → комментарий `Не в этом квартале` →
   «Отклонить» → подтвердите «Отклонить».
   → «Отклонён», дальше документ не идёт.
10. **Любой документ.** Плашка → «Демо Автор» → «Новый документ» → `12_act_errors.pdf` → «Далее: проверить документ».
    → Плашка «ИИ распознал: Акт ✦ — такого вида нет в шаблонах компании»: проверены общие реквизиты (нет даты,
    номера и подписи — только предупреждения), отправить можно. Маршрут такого документа автор составляет сам.
11. **Свой маршрут.** В любом черновике «Далее: выбрать согласующих» → «Новый этап» → «Демо Администратор» →
    перетащите его за ⋮⋮ в этап 1 или оставьте отдельным этапом → «Отправить на согласование».
    → На карточке он в маршруте с пометкой «добавлен автором». Обязательного (с замком) убрать нельзя.
12. **Компания и правила.** Плитка «Компания»: сотрудники с ролями, «Кто согласует документы», «Правила проверки»,
    показатели. Плашка → «Демо Администратор» → «Компания» → «Заявки на вступление»: у «Демо Кандидат» отметьте
    роль → «Принять»; в «Кто согласует документы» нажмите на вид — там отмечаются обязательные роли; в «Правилах
    проверки» нажмите на правило, чтобы подстроить его под компанию; закон изменить нельзя.
13. **Поиск.** На главной 🔍 → наберите `записка` → документы из всех разделов сразу.

В демонстрации уведомления в бот не приходят: согласующие вымышленные. В настоящей компании
(«Создать компанию» → код приглашения коллеге) каждый согласующий получает в боте сообщение с кнопкой
«Открыть документ», когда подходит его очередь, а автор — когда принято решение. Боту можно написать часть
названия документа — он ответит статусом.

Начать демонстрацию с чистого листа: «Компания» → «Демонстрационный режим» → «Начать заново».

```bash
docker compose up

# Полный сброс, включая БД и файлы
docker compose down -v && docker compose up --build
```

Ошибка в одном сценарии не требует перезапуска решения: состояние документа
хранится в БД, пользователь продолжает работу с того же места.

**Выкладка на стенд** (для команды; каталог проекта на сервере):

```bash
./deploy.sh              # выложить свежий main
./deploy.sh <коммит>     # откатиться на прошлую версию
```

Скрипт обновляет код, пересобирает образы, ждёт `UP` от `/actuator/health` и
показывает, какой коммит выложен. Если бэкенд не поднялся, он сам подсказывает
команду логов и откат. Выкладка — ручная: выкладывает тот, кто готов сразу
проверить результат в MAX.

## 16. Известные ограничения

Сознательные границы MVP:

- Статусы «Согласован» и «Утверждён» — внутреннее решение компании, а не юридически значимая подпись: электронной
  подписи в MVP нет.
- Пользователь состоит в одной компании. Набор ролей стандартный (Директор, Руководитель отдела, Юрист, Бухгалтер,
  Кадровик) — своих ролей компания не добавляет; при редкой роли используется ближайшая стандартная.
- Шаблоны маршрутов по видам документов создаются по умолчанию; этапы шаблона через интерфейс не редактируются.
  Администратор отмечает, какие роли в шаблоне обязательны, а автор перед отправкой меняет порядок и состав
  остальных согласующих как угодно. У «Другого документа» обязательных нет — маршрут составляет автор.
- Редактора файлов в приложении нет. Поле, найденное ИИ в DOCX, можно исправить прямо в файле:
  прежнее значение заменяется в тексте с сохранением оформления, получается новая версия. PDF так
  не правится — исправленный файл загружается новой версией.
- Работа ведётся только на синтетических тестовых документах; соответствие 152-ФЗ
  не заявляется.
- Согласующим можно поставить только активного сотрудника хотя бы с одной ролью; один человек — один раз в
  маршруте. Утверждающий — ровно один, последним этапом.
- Возврат документа на доработку перезапускает цепочку с первого этапа:
  документ изменился, значит прежние одобрения относятся к другой версии.
- Кворум «M из N» на параллельном этапе не реализован — требуется одобрение
  всех участников этапа.
- Межорганизационное согласование не реализовано.
- Сканы и фотографии без текстового слоя не распознаются: изображение нельзя замаскировать
  перед отправкой в модель. Приложение сообщает, что текста в файле нет, поля вводятся вручную.
- Удалённый черновик исчезает из приложения, но его файлы остаются в хранилище: файлы в MVP неизменяемы и не
  удаляются. Поэтому в сервис не стоит загружать настоящие чувствительные документы — только синтетические.
- Формат DOC (старый Word) не поддерживается — только PDF и DOCX. Прочитать DOC без Apache POI нельзя, а POI не
  укладывается в лимит сборки. На DOC приложение подсказывает сохранить файл как DOCX.
- Семантическая детекция произвольного чувствительного контента отсутствует:
  только регулярные выражения по структурным идентификаторам, словарь
  ключевых слов и ручной флаг автора.
- Живой интеграции с государственными реестрами нет.
- Аналитика — три показателя на списке документов (число отправленных, медианный срок согласования,
  доля возвратов); отдельного дашборда нет.
- Статус документа по названию в боте доступен только участникам реальной компании: у бота нет
  переключателя «действовать как», поэтому документы демо-песочницы он не ищет и отвечает
  предложением открыть мини-приложение.
