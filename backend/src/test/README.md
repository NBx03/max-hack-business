# Проверка схемы PostgreSQL

Из корня репозитория в PowerShell:

```powershell
./backend/src/test/run-schema-test.ps1
```

Нужны Docker Compose, Maven и Java 21. Скрипт запускает только PostgreSQL 16
в отдельном проекте со случайным именем, портом на loopback и временным хранилищем
tmpfs. Случайный пароль передаётся окружением; не сохраняется в файлах и не выводится.
В конце удаляются только созданные тестовые контейнер и сеть. Рабочий compose.yaml
и его volumes не используются.

Внутри выполняется `mvn test`. `DatabaseSchemaTest` запускает настоящее приложение
на случайном HTTP-порту дважды. Проверяются 5 changeset, Hibernate `validate`,
16 JPA-сущностей и 16 репозиториев, чтение всех моделей и запись JSONB, ограничения
PostgreSQL, `/actuator/health`, сохранность checksums при повторном запуске.
GigaChatAutoConfiguration отключена только в тесте: внешние сервисы не нужны.
Синтетические записи создаются в тестовой транзакции и откатываются.

Для отдельного PostgreSQL можно задать `SCHEMA_TEST_URL` и `SCHEMA_TEST_PASSWORD`
и выполнить `mvn test` из `backend`. Пользователь БД — `schema_test`. База должна быть
пустой и выделенной исключительно для теста: миграции сохраняются, тестовые записи
откатываются. Без `SCHEMA_TEST_URL` интеграционный тест пропускается; это не подтверждение
работоспособности схемы. Новых тестовых зависимостей нет.

## Решения схемы

- 16 таблиц соответствуют разделу 3 ARCHITECTURE.md. SQL имена используют `org_id`
  из архитектуры, в том числе в `document`; `organization_id` не вводится как дубль.
- Межмодульные ссылки в Java — скалярные ID. Нет EAGER-ассоциаций, каскадного удаления
  или обхода связей в equals/hashCode/toString. У составных ключей equals/hashCode
  сравнивает только два ID. Обычные сущности не используют Lombok Data.
- Identity BIGINT, Instant ↔ timestamptz, enum ↔ varchar с CHECK; JSON версии ↔ jsonb.
  Файловых BLOB/bytea нет. `check_status` — nullable строка: список состояний не задан
  документацией. JSON-структуры остаются гибкими, без новых контрактов API.
- `organization_member.is_demo` — техническая копия признака организации, защищённая
  составным FK. Partial unique index ограничивает ACTIVE только в реальных компаниях.
- Действующий код компании: ORG_CODE и revoked_at IS NULL. У общего кода нет срока
  действия или однократного использования. Личные токены уникальны, их срок есть в expires_at.
- Версии уникальны по (document_id, version_no). Шаг согласования ссылается на эту пару
  составным FK. Файл ссылается на version_id; максимум один MAIN обеспечивает partial index.
- Один storage_key может встречаться в разных версиях. Уникальность позиции действует
  внутри версии; позиции неотрицательные. Параллельные стадии маршрута разрешены.
- RequirementRule использует существующие enum из порта RuleEngine; expected — текст,
  его интерпретация относится к движку правил. Миграции не содержат бизнес-правил или seed.
- Changeset имеют author `sibvibe`, id `14-001-organizations` … `14-005-indexes`.
  После слияния изменяются только новыми changeset.

## Что остаётся сервисному слою

- Права доступа, членство автора/согласующего и принадлежность ролей участникам
  и личным приглашениям той же организации; назначение ADMIN отдельно от бизнес-ролей.
- Не более 10 ATTACHMENT и один обязательный MAIN для загруженного документа;
  документ-форма может хранить content без файла. Лимиты размера и MIME по содержимому.
  Конкурентные изменения версии защищаются блокировкой документа согласно архитектуре.
- Переходы состояний, соответствие current_version_no существующей версии,
  неизменяемость исторических версий и синхронизация check_status/JSON результатов.
- Проверка срока/отзыва личной ссылки, атомарное использование и назначение ролей;
  перевыпуск кода и создание/закрытие заявок в корректной транзакции.
- Политика удаления: FK запрещают появление сирот, но не заменяют бизнес-проверки.
  Файлы, используемые несколькими версиями, в MVP не удаляются.
