## 2. Архитектура в двух абзацах

**Бэкенд** — Java 21, Spring Boot 3.5.16, модульный монолит `ru.sibvibe.approval.<модуль>`: `common`, `security`,
`organization` (компании, участники, приглашения), `document` (документы, версии, файлы, проверка), `rules`
(справочник правил и настройки компании), `ai` (порты модели и их реализация на GigaChat), `approval` (маршруты,
этапы, решения), `bot` (MAX Bot API, уведомления), `storage` (MinIO), `config`. Кто кого может вызывать — ARCHITECTURE.md,
раздел 2; межмодульные вызовы идут через сервисы и порты, чужие репозитории не импортируются. `organization` и
`approval` не вызывают `bot` напрямую — публикуют события, `bot.service.NotificationListener` слушает их
`@TransactionalEventListener(AFTER_COMMIT)` + `@Async`. Схема — Liquibase (`backend/src/main/resources/db/changelog`),
Hibernate в `validate`.

**Конвейер проверки документа:** файл → текст (PDFBox / DOCX средствами JDK) → минимизация → маскирование
плейсхолдерами → `DocumentExtractor` (модель, только поля) → `RuleEngine` (обычный код) → замечания. Модель
ничего не решает; при недоступной модели поля вводятся вручную, правила работают так же. Правила — шаблон сервиса
плюс отличия компании (`organization_rule_setting`).

**Фронтенд** — React 19.2.8 (ровно) + `@maxhub/max-ui` 0.5.0 + Vite 7 (Node 22), TypeScript strict. Сборка —
статика в nginx; nginx проксирует `/api` на бэкенд, поэтому один origin и CORS не нужен. Запросы только на
относительный `/api/...`. Слой запросов — `frontend/src/api/`, логика, вынесенная из экранов в чистые функции
с тестами, — `screens/**/*.ts` рядом с экранами (например `fieldCorrection.ts`), запуск — `app/launch.ts`,
навигация — `routes/`.

## 3. Бот и мини-приложение в MAX

- Бот создан организаторами: **`@t354_hakaton_max_bot`**. Мини-приложение открывается по ссылке
  `https://max.ru/t354_hakaton_max_bot?startapp=<payload>`, payload до 512 символов `A-Za-z0-9_-`.
  Наши payload: `c_<код>` — код компании, `p_<токен>` — личное приглашение, `d_<id>` — документ.
  **Что происходит по ссылке (LNK-1, 25.09):** `c_` — заявка на вступление подаётся сама при открытии, экран «Заявка
  отправлена»; `p_` — экран с компанией и ролями, одна кнопка «Вступить», дальше главная (подтверждение нажатием —
  мера безопасности, DECISIONS.md); `d_` — карточка документа. Если человек пришёл по ссылке в **чат** с ботом
  (`bot_started` с `payload` или набранное `/start <payload>`), бот отвечает кнопкой `open_app` с тем же payload.
- Адрес мини-приложения зарегистрирован организаторами: **https://documentics.ru**. Внутри MAX открывается
  только он — поэтому проверка в MAX возможна только на стенде.
- MAX Bridge — это `window.WebApp` из скрипта `https://st.max.ru/js/max-web-app.js` в `index.html`, не npm-пакет.
  Фронтенд не разбирает `initData`, а целиком шлёт её на бэкенд в `Authorization: MaxInitData <initData>`;
  подпись и давность проверяет `security/MaxIdentityVerifier`. Идентификатор пользователя — только из проверенной
  `initData`, никогда из тела или параметров запроса.
- Выбора файла или камеры в мосте нет — загрузка через обычный `<input type=file>`. Скачивание — метод моста
  `downloadFile`.
- Кнопки в сообщениях бота — тип `open_app` (открывают мини-приложение сразу), не `link`.
- **Уведомления**: согласующим, когда подошла их очередь; автору — о решении; администратору — о заявках и
  вступлении по ссылке; напоминание о застрявшем шаге (`REMINDERS_*`). Синтетическим участникам демо-песочниц
  (`max_user_id <= 0`) бот ничего не шлёт.
- **Входящие сообщения бота** (`/start`, поиск документа по части названия) — только через webhook на стенде:
  `POST /api/v1/bot/webhook` с секретом `X-Max-Bot-Api-Secret`; без секрета — 401. Этот путь обязан быть
  исключён из фильтра проверки `initData` (`MaxAuthenticationFilter.shouldNotFilter`) — 24.09 он не был,
  и бот молчал на все сообщения (#99).
- **Навигация внутри MAX (грабли, 24.09):** у фрейма мини-приложения и страницы MAX общая история браузера,
  поэтому `history.back()` отменяет переходы самого MAX. «Назад» внутри приложения — всегда переход к логическому
  родителю с `replace` (`routes/backNavigation.ts`), без `history.back()`.
- **Повторный запуск из бота при открытом приложении:** MAX может сменить данные запуска без перезагрузки
  страницы. `app/launch.ts` ловит `hashchange`/`popstate`/`pageshow`/`focus`/`visibilitychange` и перезагружает
  страницу **не больше одного раза** на одну строку запуска (метка в `sessionStorage`) и только если есть
  `window.WebApp` — иначе возможна бесконечная перезагрузка. Поведение MAX тут не документировано; при
  проблемах смотреть в веб-версии MAX консоль, строки `[approval]`. С 25.09 перезагрузка срабатывает и тогда, когда
  хэш прежний, а мост отдал другую `initData` (LNK-2); при каждом запуске в консоль пишется, дошёл ли параметр до моста
  и до `/me` (`logLaunch`, только вид параметра — токен секретный). На бэкенде та же картина — строка
  `Запуск мини-приложения по ссылке: вид …` в `docker compose logs backend`.
- **Демо-режим** (`DEMO_MODE=true`, на стенде включён): личная песочница проверяющего с вымышленными
  сотрудниками и переключателем «действовать как» (заголовок `X-Demo-Act-As`, только внутри своей песочницы).

**Режим работы с 25.09 (решение капитана).** Основные области остаются за теми же людьми: они в первую очередь ревьюят
изменения в своей области. Но на этапе масштабных правок и новых фич **задачу может взять любой** — и менять любые
модули, которые нужны для пункта, без согласования «чужого» кода заранее. Чтобы ревью оставалось удобным, в описании PR
изменения делятся на разделы **«Бэкенд»** (смотрят Илья и Никита) и **«Фронтенд»** (смотрит Матвей). Крупную работу
режем на PR цепочкой (каждый следующий — от ветки предыдущего), чтобы ревьюить параллельно, а сливать по порядку.

Обмен между модулями — через порты и сервисы, не через общий код. Фронт ↔ бэк: `docs/API_CONTRACTS.md` —
меняете эндпоинт или DTO, правите контракт в том же PR.

**Процесс:**
- В `main` напрямую не пушим — только PR. Ветки `feature/<задача>-<кратко>`, `fix/<задача>-<кратко>`.
- Заголовок PR — `тип(область): описание по-русски (#задача)`, проверяет робот `pr-title`. Сливаем squash-ом.
- Условия слияния: зелёные `backend`, `frontend`, `testdata`, `pr-title` и одно одобрение не автора.
- Ревью — по делу и быстро (договорённость 24.09: в течение часа-двух после запроса). Блокирующее — в ревью,
  неблокирующее — ещё и в #50.
- **Документы обновляются в том же PR, что и код:** контракт, ARCHITECTURE, RULES (через генератор), README.

**Как не конфликтовать с чужим кодом:**
- Перед началом — свежий `main`; долгую ветку регулярно переносите на `main` (`git rebase origin/main`).
- **Номер миграции** берите следующий за последним в `main` *и во всех открытых PR*. Кто сливается вторым —
  переименовывает свою миграцию, правит `db.changelog-master.yaml` (include последним) и счётчики в
  `DatabaseSchemaTest`. Liquibase различает изменения по id, порядок важен только в master.yaml.
- **Уже применённую на стенде миграцию не меняем никогда** — только новая миграция. Изменение контрольной суммы
  уронит запуск бэкенда. Если правили неприменённую миграцию — всем, кто её запускал, пересоздать локальную базу.
- **PR поверх другой ветки (stacked):** база PR — ветка-предок. После squash-слияния базы переносите так:
  `git rebase --onto origin/main <старая вершина базы>`. **Не удаляйте ветку базы до перенацеливания зависимого PR
  на `main`** — GitHub закроет зависимый PR (так было с #97; чинится: вернуть ветку базы, вернуть головной коммит
  PR, переоткрыть, перенацелить).
- Правила и поля документов меняются только в `testdata/rules.json` → `python testdata/generate.py`
  (перегенерирует `docs/RULES.md`, `expected.json`, тестовые документы) → миграция. CI проверяет
  `generate.py --check`, а `DatabaseSchemaTest` построчно сверяет базу с `rules.json`.
- Не трогайте чужой открытый PR без договорённости; если перенесли чужую ветку — напишите в PR, что сделали.

## 5. Запуск и разработка

**Всё решение одной командой** (так же проверяют жюри):
```bash
cp .env.example .env && docker compose up --build
```
Сервисы: `postgres`, `minio`, `minio-init`, `backend`, `frontend`. Порты — только на `127.0.0.1`
(`BACKEND_PORT`, `FRONTEND_PORT`).

**Переменные окружения** (`.env.example`; значения секретов — только в локальном `.env` и на стенде):

| Группа | Переменные |
|---|---|
| База | `DB_NAME`, `DB_USER`, `DB_PASSWORD` |
| Файлы | `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, `MINIO_BUCKET` |
| Модель | `AI_ENABLED`, `AI_PROVIDER`, `GIGACHAT_CREDENTIALS`, `GIGACHAT_CLIENT_ID`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL` (по умолчанию `GigaChat-2-Max`), `AI_TIMEOUT_SECONDS` |
| Бот | `MAX_BOT_TOKEN`, `MAX_BOT_ENABLED`, `MAX_BOT_API_URL`, `MAX_BOT_UPDATE_MODE` (`polling`/`webhook`), `MAX_BOT_WEBHOOK_URL`, `MAX_BOT_WEBHOOK_SECRET`, `MAX_MINI_APP_URL` |
| Прочее | `DOWNLOAD_LINK_SECRET`, `DEMO_MODE`, `REMINDERS_ENABLED`, `REMINDERS_CRON`, `REMINDERS_STUCK_AFTER_HOURS`, `REMINDERS_COOLDOWN_HOURS`, `BACKEND_PORT`, `FRONTEND_PORT` |

**Разработка без MAX:**
- бэкенд с профилем `dev` принимает `Authorization: Dev <maxUserId>`; без профиля `dev` такой заголовок — 401;
- фронтенд `npm run dev` (Vite проксирует `/api` на `VITE_API_TARGET`, по умолчанию `localhost:8080`); вне MAX
  подставляется `Dev`-заголовок, второй пользователь — `?devUser=2` в адресе (запоминается во вкладке). В сборке
  для прода этой заглушки нет;
- бот локально — только у того, кто сейчас его проверяет, режим `polling`; у остальных `MAX_BOT_ENABLED=false`.
  **Никогда локально:** `MAX_BOT_UPDATE_MODE=webhook` и `DELETE /subscriptions` с настоящим токеном — это снимет
  подписку стенда, и бот замолчит для всех (подробно — CONTRIBUTING.md).

## 7. Стенд и выкладка

- **https://documentics.ru** — Ubuntu 24.04, Docker compose-проект `max-approval` в `/var/docker/max-hack-business`,
  `.env` рядом (секреты — только там). HTTPS — Caddy на хосте → `127.0.0.1:8081` (nginx фронтенда).
- На стенде включены `AI_ENABLED=true` (GigaChat-2-Max) и `DEMO_MODE=true`; бот — в режиме webhook.
  **Раз модель включена, любое изменение промпта или разбора ответа модели — только с живым прогоном
  до и после** (так 24.09 нашли, что общий промпт «поля + сводка» ломал извлечение, #104).
- Доступ по SSH — только у тех, кому его выдал Булат. Выкладка:
  1. дамп базы перед выкладкой (скрипт `/tmp/backup-008.sh` пишет в `/root/backups/approval-*-before-deploy.sql.gz`;
     если его нет — `pg_dump` через `docker compose exec postgres`);
  2. `cd /var/docker/max-hack-business && ./deploy.sh` — выкладывает `origin/main`; `./deploy.sh <коммит>` — откат.
     Каталог должен быть чистым (без локальных правок);
  3. проверить: фронтенд отвечает 200; `POST /api/v1/bot/webhook` без секрета — 401; последняя запись
     `databasechangelog` — ожидаемая миграция; в `docker compose logs backend` нет `ERROR`.
- Выкладываем после каждого слияния, которое меняет поведение; перед показом команде — обязательно.
- С хоста к `platform-api2.max.ru` — только `curl --cacert backend/certs/russian_trusted_root_ca.pem`.

## 8. Известные грабли (коротко; полный список ловушек стека — CLAUDE.md)

- Образы MinIO — `quay.io/minio/minio`, `quay.io/minio/mc` (на Docker Hub их больше нет).
- Bot API — `platform-api2.max.ru`, токен только в заголовке `Authorization`; сертификаты Bot API и GigaChat —
  от корня Минцифры, он встроен в образ бэкенда, проверку сертификатов не отключаем.
- Секрет webhook — только `A-Za-z0-9_-` (`openssl rand -hex 32`), с `+/=` подписка молча не проходит.
- Apache POI не используем (сборка выходит за лимит); DOCX — zip с `word/document.xml`.
- Модель изредка отвечает некорректным JSON — `GigaChatDocumentExtractor` делает один повтор в пределах того же
  тайм-аута (#107). Прямые кавычки в тексте модели ломают JSON — не просите модель писать свободный текст внутри
  JSON-ответа с полями.
- Подсказки полей (`document_type_field.hint`) — часть промпта: неточная подсказка = неверное поле = ложное
  критичное замечание. Меняются через `rules.json` + новую миграцию, проверяются живым прогоном.
- Windows: bash-heredoc с тройными кавычками ломается — скрипты правки писать отдельным файлом; Git Bash `ssh`
  не видит ssh-agent Windows — использовать `C:\Windows\Sysnative\OpenSSH\ssh.exe`.
- Тестовая база в контейнере — без `--rm`, иначе исчезает при остановке.
