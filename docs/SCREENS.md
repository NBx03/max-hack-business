# Экраны мини-приложения

> **UI/UX — по [review-round-1/REVIEW-ROUND-1.md](review-round-1/REVIEW-ROUND-1.md), дизайн-принципы в §2.**
> Этот файл описывает логику экранов (какие данные, запросы, состояния) и переписывается по мере переделки
> (задача #108): разделы, помеченные «переделывается», описывают старый интерфейс и **не образец** — раскладку,
> названия и стили берите из review и [DECISIONS.md](review-round-1/DECISIONS.md).

Что на каждом экране, какие действия и состояния. Визуальный стиль — дизайн-система `frontend/src/ui/`
поверх `@maxhub/max-ui`. Данные экранов — в [API_CONTRACTS.md](API_CONTRACTS.md).

## Общие правила для всех экранов

- **Четыре состояния у каждого экрана с данными:** загрузка (скелетон или `Spinner`),
  данные, пусто (текст + следующее действие), ошибка (текст из `message` + «Повторить»).
  Исключение — ошибка конкретного действия (решение по шагу, отправка на маршрут):
  у неё нет своего «Повторить», нажатие на кнопку действия и есть повтор; текст `message`
  просто выводится (`ErrorText`), без второй, ничего не повторяющей кнопки рядом.
- **Главное действие экрана — одна заметная кнопка внизу.** Второстепенные — выше и тише.
- **Ошибки бэкенда показываем его текстом** (`message`), не пишем свои.
- **Кнопки, которых нельзя нажать, не показываем**, а не делаем неактивными — кроме
  случаев, когда нужно объяснить почему (отправка при замечаниях, пустая роль).
- **Статусы различимы не только текстом:** своя метка с цветом и значком у каждого статуса.
- **Нижнее меню разделов «Документы» и «Компания»** — на списке документов, в разделе
  «Компания» и на экранах администрирования. Без него после создания компании человек
  оставался на «Приглашении» и не видел пути к документам (тест 23.09). На «Компании» —
  счётчик новых заявок для администратора.
- **Назад.** На некорневых экранах над заголовком — ссылка «‹ Документы» / «‹ К документу» /
  «‹ Компания»: системную кнопку MAX замечают не все. Она и системная `WebApp.BackButton`
  (`routes/useMaxBackButton.ts`) ведут в одно место — к логическому родителю экрана
  (`routes/backNavigation.ts`): проверка и маршрут → карточка, карточка и загрузка → список,
  администрирование → «Компания». Переход к родителю **всегда заменяет текущий экран**, а не
  делает шаг назад по истории браузера: в веб-версии MAX у фрейма приложения и страницы MAX общая
  история, и `history.back()` отменял переход самого MAX — «‹ Документы» переставала работать
  (приёмка 24.09, п. 6 и 11). На корневых экранах (список, «Компания», приветствие, ожидание решения)
  системная кнопка скрыта.
- **Повторное открытие из бота.** Кнопка уведомления при уже открытом мини-приложении
  ведёт на нужный документ: запуск отличается по данным запуска, а не по пути
  (`app/launch.ts`), поэтому ссылка отрабатывает на любом экране. Новые данные запуска в адресе
  ловятся по `hashchange`, `popstate`, `pageshow`, `focus` и `visibilitychange`. Как клиент MAX
  передаёт повторное открытие, в документации моста не описано, поэтому сообщения моста пишутся
  в консоль с меткой `[approval]` (уровень debug) — для проверки на конкретном клиенте.
- **Ссылка важнее демонстрации.** Человек без компании, которого приложение вернуло бы в демонстрацию,
  при открытии по ссылке (приглашение, документ) попадает по ссылке.
- **Демо-режим:** в углу — плашка «Демо: действую как <имя>», по нажатию — список
  участников своей песочницы, «Начать заново» и «Выйти из демо». Показывается, когда
  фронтенд работает в песочнице (`/me.actingAs` не пустой).

- **Ширина:** на широком окне (веб-версия MAX) всё приложение — плашка демо, экран и нижнее меню —
  одна колонка 560 px по центру с границами по бокам, поле вокруг — вторичным фоном (`.app-frame`,
  `theme/tokens.css`). Раньше меню растягивалось на всю ширину, а контент стоял узкой колонкой
  (приёмка 24.09, п. 14). Отдельной десктопной вёрстки нет.
- **Тексты — коротко.** Подпись — одна строка по делу, без пересказа того, как устроен сервис;
  второстепенный текст — не мельче 13 px (приёмка 24.09, п. 5).
- **Роли выбираются одним компонентом везде** — на заявке, в участнике, в личной ссылке:
  чипы выбранных ролей с «×» и кнопка «+», открывающая список оставшихся ролей компании.
  «Права администратора» — отдельный переключатель рядом, не чип: это не роль.
- **Тексты замечаний и источники — только из бэкенда** (`message`, `sourceTitle`, `sourceRef`);
  примеры для вёрстки — [RULES.md](RULES.md). Демо-документ — служебная записка.

| Статус | Текст | Цвет метки | Смысл для пользователя |
|---|---|---|---|
| `DRAFT` | Черновик | серый | Правит только автор; до первой отправки больше никто не видит |
| `IN_APPROVAL` | На согласовании | оранжевый | Идёт по маршруту |
| `RETURNED` | Возвращён | жёлтый | Нужно исправить и отправить заново |
| `REJECTED` | Отклонён | красный | Окончательно, дальше пути нет |
| `APPROVED` | Согласован | зелёный | Окончательно, документ неизменяем |

Цвет не единственный признак: у метки всегда есть текст (и значок, если он есть в
компонентах). Цвета берутся из переменных темы, чтобы метка читалась и в тёмной теме.

Решение по шагу маршрута — так же, **один цвет на одно значение**, на карточке и в истории
одинаково: «Ждёт» (оранжевый), «Согласовано» (зелёный), «Возвращено» (жёлтый, как статус
`RETURNED`), «Отклонено» (красный), «Пропущено» (серый), «Согласовано автором» (зелёный,
с пояснением «роль есть только у автора»).

## Навигация

```
Запуск → GET /me
 ├─ нет компании, нет заявки ──→ 1. Приветствие
 ├─ есть заявка на рассмотрении ─→ 5. Ожидание решения
 ├─ startParam c_<код> ─────────→ 4. Присоединение (код подставлен)
 ├─ startParam p_<токен> ───────→ 4б. Вступление по личной ссылке (SHOULD)
 ├─ startParam d_<id> ──────────→ 11. Карточка документа (из уведомления бота)
 └─ есть компания ──────────────→ 8. Список документов          ┐ нижнее меню
                                    ├─ нажали документ → 11. Карточка ├ «Документы» | «Компания»
                                    └─ «Новый документ» → 9. Загрузка ┘
                                  8а. Компания
                                    ├─ администрирование → 3, 6, 7
                                    └─ демо-компания: открыть / начать заново / выйти
```

Песочница не влияет на навигацию: `/me.membership` — только реальная компания.
Демо включается с экрана приветствия или из раздела «Компания» (в том числе участником
реальной компании) и выключается «Выйти из демо».

## Подключение компании

### 1. Приветствие
- Заголовок, строка о сервисе и три коротких пункта: проверка до отправки, понятный маршрут,
  уведомления в MAX (приёмка 24.09: экран был пустым, текст мелким).
- Кнопки закреплены внизу: **«Создать компанию»**, «Присоединиться по коду» и негромкая
  «Посмотреть демонстрацию» (только при `demoMode`; если `/me.sandbox` уже есть — «Продолжить
  демонстрацию», без пересоздания). Демонстрация подаётся как знакомство с продуктом, а не как режим работы.
- Человек без компании, который был в демонстрации, при следующем открытии возвращается туда же
  (запоминается в браузере); сотрудник настоящей компании всегда открывает свою компанию.
- Состояний данных нет — экран статичный.

### 2. Создание компании
- Поле «Название компании» — обязательное.
- Поле «ИНН» — необязательное, с подсказкой «не проверяется».
- Кнопка **«Создать»**. Создатель становится администратором и получает роль «Директор».
  После — сразу на 3. Приглашение с подсказкой «Пригласите сотрудников. Пока их нет,
  документы, где согласует директор, будут согласованы вами автоматически — это видно
  в истории».

### 3. Приглашение (администратор)
- Блок «Код компании»: крупно код, под ним ссылка `https://max.ru/t354_hakaton_max_bot?startapp=c_<код>`
  (ссылку и код даёт бэкенд). В коде нет символов 0, 1, O, I, L — в примерах тоже.
- Кнопки: **«Поделиться»** (системный шаринг MAX), «Скопировать код».
- Ниже — «Перевыпустить код» с подтверждением: «Старый код перестанет работать.
  Уже поданные заявки останутся».
- *SHOULD.* Блок «Личные приглашения»: кнопка «Создать личную ссылку» → выбор ролей
  (тот же компонент ролей, без прав администратора) → предупреждение «Вступит тот, кто откроет
  первым. Отправляйте только в личные сообщения» → ссылка и «Поделиться». Список
  неиспользованных ссылок: роли, срок, «Отозвать».

### 4. Присоединение по коду
- Поле кода (8 символов, заглавные, без пробелов). Если пришли по ссылке — уже заполнено.
- После ввода — название компании: «Вы вступаете в „ООО Ромашка“».
- Кнопка **«Отправить заявку»** → 5.
- Ошибки: «Код не найден», «Слишком много попыток, попробуйте через час».

### 4б. Вступление по личной ссылке — SHOULD
- Компания и список ролей, которые получит человек.
- Кнопка **«Вступить»** — без неё ничего не происходит.
- Ссылка использована, просрочена или отозвана — объяснение и кнопка
  «Присоединиться по коду».

### 5. Ожидание решения
- «Заявка отправлена в „<компания>“. Мы сообщим в чате, когда администратор её рассмотрит».
- Кнопка «Отменить заявку» с подтверждением.
- При повторном открытии приложения — снова этот экран, пока заявка не решена.

### 6. Заявки (администратор)
- Список: имя, когда подана.
- В строке заявки — выбор ролей (общий компонент: чипы и «+»), отдельный переключатель «Права
  администратора» и две кнопки: **«Принять»** и «Отклонить». «Принять» неактивна,
  пока не выбрана хотя бы одна роль.
- Пусто: «Новых заявок нет».

### 7. Участники (администратор)
- Список: имя, роли метками, отметка «Администратор».
- Нажатие — выбор ролей (тот же компонент) и отдельный переключатель «Права администратора», «Сохранить».
  Права администратора — не роль: в маршрутах они не участвуют.
- Ошибки показываются текстом бэкенда: «Нельзя снять права администратора с последнего администратора».
- «Исключить из компании» — сразу, с подтверждением: «Документы, которые ждут решения сотрудника, вернутся авторам».
  Под выбором ролей, когда роль снимается, — та же оговорка для снятой роли (приёмка 24.09, п. 15: раньше исключить
  человека с незавершёнными согласованиями было нельзя). После сохранения или исключения сообщение называет, сколько
  документов вернулось авторам: «2 документа вернулись авторам — их можно отправить заново».
- Исключённые — не в общем списке, а свёрнутым блоком «Исключённые · N» внизу: запись остаётся ради истории
  решений, вернувшийся по коду или ссылке человек занимает прежнее место.

## Документы

### 8. Список документов — главный экран
- Вкладки: **«Ждут меня»** (со счётчиком), «Мои», «Доступные мне». Вкладка и фильтры запоминаются
  на время работы с приложением: вернувшись из карточки, человек видит тот же список (приёмка 24.09,
  п. 3). «Ждут меня» — только при первом открытии.
- Фильтры: статус, тип, автор, период — в нижней панели по кнопке «Фильтры».
- Строка: название, тип, метка статуса, автор, дата. Во «Ждут меня» — «ждёт N дней»
  со склонением («1 день», «2 дня», «5 дней»); за 0 дней (сегодня) — «ждёт с сегодня».
- Кнопка **«Новый документ»**.
- Пусто: во «Ждут меня» — «Ничего не ждёт вашего решения»; в «Мои» —
  «Документов пока нет» и «Новый документ».

### 8а. Компания
- Название компании (в демо — «Демонстрационная компания с вымышленными сотрудниками»), кто я: имя, роли.
- «Сотрудники · N» — всем участникам (`GET /orgs/current/colleagues`): имя и роли; администратору — «Управлять».
- Администратору — «Пригласить сотрудников», «Заявки на вступление» (со счётчиком), «Участники и роли».
- «Правила проверки» → 8б — всем участникам; подпись у администратора «…и настройка под компанию».
- «Маршруты согласования» (`GET /orgs/current/routes`): для каждого вида документа — роли этапов по порядку,
  «(если есть)» у необязательных; подпись «Перед отправкой автор может добавить согласующих» (приёмка 24.09, п. 2).
- «Показатели согласования» (переехали со списка документов): сколько обычно проходит от отправки до
  «Согласован» и какую долю документов возвращали; меньше часа — словами.
- «Как устроено согласование» — пять шагов без названия модели: подготовка, исправление, маршрут, решения,
  результат.
- При `demoMode` внизу — «Демонстрационный режим»: вне демо «Открыть/Продолжить демонстрацию», внутри —
  «Выйти из демонстрации» и «Начать заново».

### 8б. Правила проверки (#91)
Кто сюда приходит: автор или согласующий — понять, откуда замечание; администратор — подстроить типовые
правила под документы компании.
- Подпись: администратору «Типовые правила сервиса. Нажмите на правило, чтобы подстроить его…», остальным —
  «…Менять их может администратор». Если что-то настроено — «Изменено компанией: N».
- «Вид документа» — выбор (как на загрузке, «Другой документ» последним).
- Карточка правила: **что проверяется словами** («Кому» заполнено, «Текст» — не короче 50 символов, «Вид отпуска» —
  одно из: …), важность меткой («Критично» / «Предупреждение» / «Совет», или «Не проверяется»), текст замечания,
  основание одной строкой — без пояснения в скобках («Правило компании: ГОСТ Р 7.0.97-2016 «…», п. 5.15»;
  название, которое ввела компания, не сокращается;
  у рекомендации сервиса — просто «Рекомендация сервиса»), метки «🔒 Закон — не меняется» и «Изменено компанией».
  Порядок — по полям документа, внутри поля — сначала «заполнено».
- Администратор нажимает на правило → шторка: «Проверять это правило»; важность с пояснением («Документ нельзя
  отправить, пока не исправят» / «Замечание видно, отправить можно» / «Мягкая подсказка»); «Не короче, символов» или
  «Допустимые значения — по одному в строке» (только у этих проверок); «Текст замечания — его увидит автор»;
  «Основание — документ компании» и пункт; «Сохранить», «Сбросить к типовому» (если изменено). Подпись: действует
  для новых проверок, черновики — после «Проверить заново», документы на согласовании не меняются.
- У закона вместо формы — «Требование закона одинаково для всех компаний — выключить или ослабить его нельзя».
- Остальным участникам карточки не нажимаются.
- Внизу: «Новые правила и поля добавляются в шаблон сервиса, а не здесь».
- Ссылка `/company/rules?rule=<id>` сразу выбирает вид документа и, у администратора, открывает правило.

### 9. Загрузка документа
> Переделывается (UPL-1…3, UPL-6, DOC-7 — PR 4 из #108): описание ниже — старый интерфейс, не образец.

- Над выбором файла — «Нет файла? Служебную записку можно заполнить прямо здесь» с кнопкой «Заполнить» → 9а
  (только если тип «Служебная записка» есть в справочнике).
- Основной файл: кнопка выбора, имя и размер после выбора, «Заменить».
- Тип документа: **по умолчанию «Определить автоматически»** — вид выбирает ИИ; дальше
  типы с подробной проверкой и «Другой документ» (общие реквизиты). Под выбором — что
  именно будет проверено (#86: раньше по умолчанию стоял «Любой файл» без проверки, и человек
  со своим файлом ИИ не видел вовсе).
- Название — необязательное: «Необязательно — возьмём из документа».
- *SHOULD.* Приложения: «Добавить приложение», список с «Убрать», до 10.
- Видимость: «Только участники согласования» / «Вся компания».
- Переключатель «Содержит чувствительные данные»: текст не отправляется в ИИ, тип выбирается
  вручную («Определить автоматически» недоступно), ниже появляются поля типа для ручного ввода.
- Кнопка **«Загрузить и проверить»**. Во время запроса — «ИИ читает документ, затем правила
  проверяют найденные поля. Это займёт до минуты».
- После — 10. Результат проверки.

### 9а. Служебная записка в приложении — SHOULD (#59)
- Документ-форма без файла, подпись одной строкой: «Файл не нужен: правила проверят записку сразу».
- Поля типа «Служебная записка» по порядку схемы: кому, от кого (по умолчанию — имя текущего пользователя), дата
  (по умолчанию сегодня), номер, заголовок, текст (многострочный), должность и расшифровка подписи.
- Название — необязательное: «возьмём заголовок записки». Видимость — как на 9.
- Кнопка **«Проверить»**: без распознавания, правила проверяют поля сразу → 10.
- Нет типа в справочнике — «Служебные записки в компании не настроены. Загрузите документ файлом».

### 10. Результат проверки
> Переделывается (UPL-3, DOC-7 — PR 4 из #108): описание ниже — старый интерфейс, не образец.

- Под заголовком: тип, «вид определил ИИ», если так, версия; автору черновика — «Сменить тип»
  (документ проверяется заново по правилам выбранного типа).
- «Как проверялся документ» (свёрнуто, раскрыто без модели): ИИ (GigaChat) нашёл поля в тексте,
  правила проверили их, решение принимают люди. Без модели — почему поля не заполнились сами.
  Файл без текста (скан, фото): «В файле нет текста — похоже, это скан…», поля вручную (`check.textMissing`).
- Блок «Замечания»: сначала критичные, потом предупреждения и подсказки. Каждое: важность
  меткой, текст, поле, источник правила с видом — тем же словарём, что в «Правилах проверки»: «Закон», «Правило компании»,
  «Рекомендация сервиса»
  и ссылкой, цитата из документа и страница, если есть.
- Нет замечаний: «Замечаний нет» — явно, а не пустой блок.
- У черновика и возвращённого документа рядом с заголовком «Замечания» — **«Проверить заново»** (#90): по текущим
  правилам компании, по тем же полям, без повторного чтения файла. Нужна, когда администратор поменял правила после
  проверки. У возвращённого проверяется новая версия-черновик с теми же файлами и полями.
- Администратору у основания каждого замечания — «Настроить правило» → 8б с открытым правилом. Важность «Совет»
  (а не «Подсказка») — те же слова, что в «Правилах проверки».
- Проверка не выполнилась (`check.status = FAILED`): «Проверка не выполнена». Отправка недоступна.
- Блок «Данные документа»: у каждого поля — откуда значение: «Из текста документа: «цитата»»,
  «Указано вручную» или «Изменено вручную, файл не менялся. В файле: «…»» (виден и согласующему).
  **Одна** кнопка правки — «Изменить» у этого блока; когда есть критичные замечания или документ
  возвращён, она главная (синяя). Внизу экрана кнопки правки полей нет (приёмка 24.09, п. 7).
- Форма правки (#86):
  - DOCX (`canCorrectFile`): **«Исправить и проверить»** — значения вписываются в сам
    файл на место прежних, с тем же оформлением; новая версия проверяется заново. Изменённым
    считается поле, которое отличается от **того, что в файле** (`fileValue ?? value`). Пустое значение
    не вписывается (иначе вырезало бы текст), поле, которого в файле нет, — сразу с объяснением.
    Что вписать не удалось — списком с причиной, а введённые значения остаются в форме. Проверка
    новой версии не выполнилась — сообщение об этом, а не «проверена заново». Второстепенно:
    «Сохранить, не меняя файл» — ИИ прочитал поле неверно или поля нет в файле.
  - PDF: «Сохранить и проверить» с пояснением, что сам PDF так не исправить, и «Заменить файл».
  - `RETURNED`: та же форма. Возвращённая версия не меняется, поэтому сохранение сначала создаёт
    новую версию с теми же файлами — документ становится черновиком (приёмка 24.09, п. 9 и 10).
- **Каждое действие — в одном месте.** Вверху, рядом с типом и версией: «Сменить тип» (черновик) и «Заменить
  файл» (черновик и `RETURNED`, в том числе у черновика без замечаний). «Заменить файл», а не «Другой файл»: это
  новый файл того же документа (п. 8). Внизу — только куда дальше: **«К маршруту»** → 12 и «Сохранить черновик»
  (ведёт на карточку с сообщением «Черновик сохранён»); при критичных замечаниях — только «Сохранить черновик».
  Во время правки полей «Сменить тип» и «Заменить файл» скрыты.
- **Документ-форма (#59, `versions[].content`)**: «Сменить тип» и «Заменить файл» нет; «Как проверялся документ» —
  «Записка заполнена в приложении — правила проверили её поля» (свёрнуто). «Изменить» правит саму записку, в том
  числе у `RETURNED`: сохранение создаёт новую версию формы целиком (не «с теми же файлами»).

### 10а. Замена файла
- Текущий основной файл, выбор нового («Новый файл»), приложения — `Switch` «Оставить»,
  «Содержит чувствительные данные».
- **Без нового файла** версия переносит поля прежней, в том числе ручные правки, и перепроверяет их
  правилами без модели (файл не изменился). Кнопка «Загрузить и проверить» доступна, если выбран
  новый файл, изменился набор приложений, включены чувствительные данные (поля вводятся здесь же)
  или документ возвращён — тогда так переходят к правке полей, не меняя файл.
- Подсказка под выбором файла — только формат и размер: поля правятся на экране проверки.

### 11. Карточка документа
> Переделывается (DOC-1…3 — PR 2 из #108): описание ниже — старый интерфейс, не образец.

Порядок сверху вниз:
1. Название, тип, метка статуса, автор.
2. **Маршрут**: этапы по порядку; в этапе — участники «Роль — Имя» и их решение меткой.
   Автоматическое согласование подписано: «согласовано автором как Директор».
   Параллельный этап — одной группой с подписью «согласуют параллельно». Активный этап выделен.
3. Файлы текущей версии: основной и приложения, нажатие — скачивание. У документа-формы (#59) вместо
   файлов — «Содержание»: поля записки с подписями, текст с переносами, «Заполнено в приложении, без файла».
4. Замечания проверки — свёрнуто, со счётчиком; нажатие ведёт на 10 (результат проверки).
   Если автор менял поля вручную без правки файла — подпись «Автор изменил вручную полей: N».
5. История: решения с комментариями и номером версии; прошлые версии.

Кнопки внизу — по `permissions` из ответа:
- Согласующий на активном этапе: **«Согласовать»**, «Вернуть», «Отклонить» — по каждому
  своему активному шагу (`myActiveStepIds`). Если у человека два шага в этапе
  (например, он и юрист, и бухгалтер) — два блока кнопок с подписью роли.
  «Вернуть» и «Отклонить» открывают поле комментария — отправить без комментария нельзя.
  Подтверждение: «Отклонение окончательное». Ошибка решения (например, 409 —
  другой согласующий уже решил) — текстом над кнопками, карточка сама обновляется.
- Автор при `DRAFT`, но `canSubmit = false` (есть BLOCKER из 10): **«Исправить
  замечания»** → 10, туда же, куда ведёт пункт 4 — без этой кнопки черновик с
  замечаниями был тупиком.
- Автор при `RETURNED`: **«Исправить документ»** → 10: там замечания, «Изменить» и «Заменить файл».
  У документа-формы (#59) — «Исправить записку» → 10; «Отправить заново без изменений» создаёт версию с той же
  формой. В «Изменения с версии N» у формы — только поля, без строки «Изменён текст документа».
  Раньше кнопка вела сразу на загрузку файла, хотя чаще нужно поправить поле. Второй кнопкой —
  «Отправить заново без изменений»: новая версия с теми же файлами и полями и сразу 12 (документ вернули
  из-за маршрута, а не из-за текста — тогда одобрения прошлой версии сохраняются).
- Над маршрутом — «Изменения с версии N» (`changes`): какие файлы заменены или добавлены, какие поля
  изменились «было → стало»; «Документ не менялся», если ничего. Согласующему повторного круга не нужно
  перечитывать документ целиком (приёмка 24.09, п. 1).
- Документ вернулся, потому что согласующего исключили или сняли с него роль (`MEMBER_REMOVED`), — плашка
  «Вернулся автоматически: <имя> больше не согласует как <роль>. Отправьте заново…». В маршруте его шаг — «Выбыл».
  Перенесённое одобрение — «Согласовано ранее».
- Автор при `DRAFT`: «К маршруту».
- `APPROVED`, `REJECTED` — кнопок нет, только скачивание.

### 12. Предпросмотр маршрута
> Переделывается (конструктор маршрута RTE-1…6 — PR 2 из #108): описание ниже — старый интерфейс, не образец.

- Этапы по порядку, в этапе — роли и люди. Если на роль несколько кандидатов —
  выбор человека в строке; пока не выбран — строка выделена.
- Необязательный участник без носителей роли — строка «пропускается: в компании нет роли».
- Обязательная роль есть только у автора — строка «согласуете вы как <роль> — автоматически».
- Под заголовком: «Этапы идут по очереди… Можно добавить согласующих, убрать обязательных нельзя».
- **«+ Добавить согласующего»** (приёмка 24.09, п. 2 и 12): кто — сотрудник в одной из своих ролей (кроме
  автора); когда — «Первым», «Вместе с «<роли этапа>»», «Отдельно, перед «<роли этапа>»», «Последним — после всех».
  Добавленные видны в маршруте с пометкой «добавлен вами» и кнопкой «Убрать»; этапы нумеруются подряд.
- Если документ не менялся с прошлой версии, у тех, чьё одобрение сохранится, — «Согласие по версии N
  сохранится — документ не менялся» (`carryOver`).
- Проблемы (`problems`) — плашкой сверху: «В компании нет сотрудника с ролью
  „Бухгалтер“ — обратитесь к администратору».
- Кнопка **«Отправить на согласование»** — неактивна, пока есть проблемы или не выбраны люди.
- После отправки — 11. Карточка с тостом по статусу из ответа `submitDocument`: обычно
  «Отправлено. Согласующие получили уведомление»; если решать было некому (обязательная
  роль есть только у автора на каждом шаге — CLAUDE.md, проверка №10) и документ сразу
  `APPROVED` — «Документ согласован — решать было некому», иначе тост соврал бы о том,
  что кто-то ещё должен решить.
