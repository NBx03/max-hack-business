## Открытые решения D1–D7

### D1 · Формат DOC
**Принимаем DOC как файл без автоматической проверки** · Apache POI в проекте нет (убран: полная сборка шла 384 с при
лимите кейса 300 с), а HWPF, которым читается DOC, — часть того же POI; своя разборка OLE2 — неоправданный риск перед
сдачей. При этом решение B итогового решения обещает: хранить и проводить по маршруту можно любой файл. DOC ведёт себя как
PDF-скан: хранится, версионируется, идёт по маршруту, поля заполняются вручную, правила проверяют их так же · у DOC нет
ИИ-проверки. Показ — UPL-6 (поправка 25.09): никакого постоянного предупреждения про DOC; справка «?» по всем форматам,
строка «PDF, DOCX или DOC · до 10 МБ» и спокойная строка на карточке файла с ограниченной проверкой.

### D2 · Вид документа
**ИИ выбирает вид из шаблонов компании; если не подходит ни один — «Другой документ», а распознанный ИИ вид («Договор
аренды») хранится и показывается отдельно** · к виду из шаблона привязаны схема полей, правила и маршрут; у вида,
придуманного ИИ, их нет, поэтому новый тип не создаётся. Распознанный вид берётся из поля «Вид документа» (`doc_kind`),
которое модель уже извлекает у «Другого документа», — промпт не меняется · список видов компании не растёт от загрузок.
Оформление (поправка 25.09, DOC-7): главным показываем распознанный вид с иконкой ИИ, «вне шаблонов» — второстепенной
пометкой; название документа — из самого документа и не подменяется видом; в фильтре такие документы — группа «Вне шаблонов».

### D3 · Свобода автора в маршруте (поправка 25.09)
**Шаблон вида документа только предзаполняет маршрут.** Двигать можно всех, включая шаблонных и обязательных: между
этапами, менять порядок этапов, выносить в новый этап, ставить в блок «Утверждение». Убирать можно всех, кроме
**обязательных**; замок означает только «нельзя удалить». Обязательность — свойство роли в шаблоне вида документа, решает
компания. Для «Другого документа» ограничений нет. Сервер проверяет только три вещи: все обязательные роли на месте,
нет дублей, нет пустых этапов (плюс прежние: автор не согласует свой документ, пока есть кто-то ещё; обязательная роль
без носителей — `ROUTE_ROLE_EMPTY`; только у автора — шаг сразу согласован с отметкой `AUTHOR_HOLDS_ROLE`) · контролю
компании нужен факт участия человека, а не его этап; жёсткий порядок делал перетаскивание бесполезным на типичном
маршруте · отменён инвариант итогового решения «маршрут может быть только расширен» — теперь «обязательные участники не
удаляются; порядок и состав остального — на усмотрение автора». Обязательность пока задаётся только данными по умолчанию
(настройка администратором — #109, редактор состава шаблона — #98), это в ограничениях README.

Данные по умолчанию — минимум обязательных: по одной роли (Директор) у служебной записки, заявления на отпуск, заявки на
меру поддержки и заявки на командировку; у «Другого документа» обязательных нет, Директор лишь подставляется. Юриста у
меры поддержки обязательным не делаем: компания без юриста не смогла бы отправить заявку вовсе.

### D4 · Утверждение (поправка 25.09)
**Финальный блок маршрута «Утверждение» с одним утверждающим** — как гриф «УТВЕРЖДАЮ» в документообороте. По умолчанию
утверждающий — последний этап шаблона, если в нём один человек; автор может сменить (перетаскиванием или выбором), а если
прежний утверждающий обязателен — он остаётся в маршруте этапом согласования. Кнопка «Утвердить», статус в процессе
«На утверждении», итог «Утверждён»; если этапа утверждения нет (утвердить некому, кроме автора, или автор убрал
необязательного утверждающего) — итог «Согласован». «На утверждении» и «Утверждён» не хранятся в базе как статус
документа: они вычисляются в одном месте на бэкенде и отдаются готовым полем, поэтому карточка, списки, фильтр и бот
показывают одно и то же. Утверждающий может и вернуть, и отклонить · «Подписать / На подписании» создавало ощущение
юридической подписи, от которого итоговое решение ушло (решение P), а итог «Согласован» после «Подписать» выглядел бы
багом · нет подписания как понятия и отдельного статуса в базе; сноска «это не ЭП» не нужна.

### D5 · Возврат исключённого сотрудника
**Вариант (а) с подтверждением администратора:** заявка бывшего участника приходит администратору с уже отмеченными
прежними ролями — остаётся «Принять»; по личной ссылке роли берутся из ссылки, как и раньше. При исключении роли не
удаляются, так что данные есть · обещание на экране «займёт прежнее место» выполняется, и остаётся правило «каждое
вступление по коду решает администратор» · полностью автоматического возврата нет.

### D6 · Несколько ролей у человека
**Да** — связь многие-ко-многим уже в схеме (`member_role`). Элемент маршрута — **человек**, роли показываются подписью
(«Юрист · Бухгалтер»). Один человек — один раз в маршруте, без исключений (RTE-3); обязательная роль закрыта, если в
маршруте где угодно есть её носитель; если шаблон подставил одного человека в двух ролях, при предзаполнении он остаётся
один раз — на более позднем месте · совпадает с моделью данных и убирает дубли, порождённые шаблоном · шаг согласования
хранит одну роль — ту, под которой человек поставлен; раньше человек с двумя ролями этапа получал два шага.

### D7 · Собственные роли компании
**До 30.09 не делаем, справочник ролей стандартный** · в итоговом решении настройка набора ролей — COULD; шаблоны
маршрутов ссылаются на роли, а без редактора шаблонов (#98, COULD) своя роль годилась бы только для ручного добавления в
маршрут, где и так добавляется человек · компания с редкой ролью пользуется ближайшей стандартной; это в ограничениях
README.
